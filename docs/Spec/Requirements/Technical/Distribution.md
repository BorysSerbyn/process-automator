## Repository
- **The `process-automator` repository** is public, and so are its releases (its GitHub path is `REPO` in `install.sh`). `make ci` runs the checks on my Mac before a push: Go tests with `-race` (the core's, the tray's and the windows app's), the Swift tests, lint (the tray's also as built for Linux), Linux and Windows cross-compiles of the core, CGO-free Linux builds of the tray (amd64 and arm64), shellcheck, the tests of `install-app.sh`'s functions and of `build-linux-windows.sh`'s caches, the Linux package (built with the windows app, so it needs Docker, and checked to hold the tray, the windows app and the tray's icons), the windows app for arm64 too (so `make publish` finds it built), and an install test of the macOS artifact. Each step is timed (`scripts/timed.sh`): its time is printed as it ends, recorded in `build/timings.tsv`, and summed up at the end, longest first; steps inside another (the windows app's Docker build, automator-ui's Swift build) are listed with `· ` and left out of the total. `RACE=` runs the Go tests without the race detector (`make test RACE=`); `make ci` keeps it. automator-ui's release build has its own build folder (`automator-ui/.build-release`), apart from `swift test`'s `.build`. The GitHub Actions workflows that ran them (and the Linux install test) on every push are kept, disabled

## Versioning
- **One version source: git tags** `vX.Y.Z`, embedded at build time into the Go binary (linker flags) and the Swift app (`CFBundleShortVersionString`), so both report the same version
- **Untagged builds** get a dev version: `<next patch>-dev+<sha>` (`.dirty` with uncommitted changes), and `0.1.0-dev+<sha>` before the first tag; the first release is `v0.1.0`
- `make release PART=major|minor|patch` bumps and tags

## Build identifiers
| What | Value |
|---|---|
| CLI | `procauto` (`Command`) |
| Bundle ID | `<BUNDLE_PREFIX>.procauto` (`BUNDLE_PREFIX` defaults to `dev`) |
| The core's signing identifier | The bundle ID, so the notify plugin's notifications are the app's |
| macOS login items | `<prefix>.procauto.ui`, `<prefix>.procauto.scheduler` |
| Linux login items | `procauto-tray.desktop` (XDG autostart entry), `procauto-scheduler.service` (systemd user unit) |
| Secrets service | `<prefix>.procauto`, the bundle ID |
| Development signing identity | `Process Automator Dev` (`SIGN_IDENTITY`, `<Name> Dev`) |

- **Said three times, kept in step**: the binary's `automator.App`, `install.sh` (`NAME`, `COMMAND`, `FOLDER`, `REPO`, `TEAM_ID`, `PUBLIC`) and the Makefile (`BUNDLE_PREFIX`); `cmd/procauto`'s test fails when they differ. The Makefile reads the names from `install.sh`, and the build writes them into `install.env` (for the installer) and the app's `Info.plist` (`CFBundleName`, `ProcAutoCommand`), which automator-ui reads its name and its CLI from; the Linux tray reads `install.env` itself

## Building another app
- **The build is parameterised**: another app runs this repository's Makefile targets (`build`, `bundle`, `package`, `package-linux`, `install`, `uninstall`) from a checkout at the version its `go.mod` pins, passing its own `INSTALL_SH` (its names), `GO_DIR` and `MAIN` (its module and main package), `TEMPLATES`, `LOGO` (a folder with `AppIcon.icns`, `glyph.svg`, `dot.svg`; the Linux tray's icons are made from it too), `BUNDLE_PREFIX`, `SOURCE_DIR`, `BUILD` and `VERSION`
- **One automator-ui, one automator-tray and one automator-windows** serve every app: none has names of its own; the bundle, or the Linux package, gives them the app's
- **Its scripts are this repository's**: `scripts/bundle.sh`, `package.sh`, `install-app.sh`, `test-install.sh` (`INSTALL_SH` for the app's installer) and `version.sh` take the app's names from `install.env` or its `install.sh`; its `install.sh` is this one with its own names in the header

## Releases
- **Built from git tags on my Mac**: `make publish` (`scripts/publish.sh`), at a commit tagged `vX.Y.Z`, builds every artifact with the repository's `make package` and `make package-linux`, signs the macOS app with the given identity or `.p12` (a throwaway keychain), runs the install test (each step timed as in `make ci`, in `build/release/<tag>.timings.tsv`), then pushes the tag and publishes them as its GitHub release with the app's `install.sh` and a `SHA256SUMS` file listing them all; nothing is pushed unless every step passed. Its notes (shown in Manage Updates) are `RELEASE_NOTES` (a file) if given, else the version's line in the repository's `docs/Progress.md` (`- X.Y.Z, on <engine> A.B.C: first; second`, as bullets), else the commit subjects since the previous release (`scripts/release-notes.sh`), followed by GitHub's changelog link. An app built on the engine runs the same script from its repository, with its own `install.sh` (`INSTALL_SH`, which must install that repository's releases)
- **macOS**: `<Folder>-<version>-macos.zip` (`process-automator-…`), the `.app` with the Go core inside, for Apple silicon (there's no Intel build), zipped with `ditto`. Signed with a Developer ID (hardened runtime) and notarized with the ticket stapled when the release workflow has one (`APPLE_DEVELOPER_ID_P12_*`, `APPLE_API_KEY_*`); otherwise with a self-signed certificate (`SIGNING_CERT_P12_BASE64`, `SIGNING_CERT_PASSWORD`), the same for every release
- **Linux**: `<Folder>-<version>-linux-<amd64|arm64>.tar.gz`: `bin/<Command>`, `bin/automator-tray` (both CGO-free), `bin/automator-windows` (cgo, built in Docker: `scripts/build-linux-windows.sh`, `scripts/linux-windows.Dockerfile`; left out with `LINUX_WINDOWS=none`. A binary built from the same inputs (the tray folder's files, the architecture, `go.mod`'s Go version, the Dockerfile) is copied from the build cache, `~/Library/Caches/process-automator-build` on macOS (`$XDG_CACHE_HOME/process-automator-build` elsewhere, `PA_BUILD_CACHE` to move it), which keeps the newest 8; `NO_BUILD_CACHE=1` builds anyway. Go's module and build caches are the Docker volumes `automator-windows-gomod-go<version>` and `automator-windows-gocache-go<version>`; those and the build image of another Go version are removed when it builds) and `share/<Folder>/` (templates, the installer, the systemd unit, autostart entry and app menu entry templates, and the tray's icons in `tray/`)
- **Every artifact carries its installer** (`install-app.sh`) and what the build named things (`install.env`: the app's name, command and folder, version, bundle ID, login item labels, secrets service), next to its templates: `Contents/Resources/` in the `.app`, `share/<Folder>/` in the Linux tree
- **Pinned once**: the repository releases come from (`REPO`), whether they're public (`PUBLIC=1`; empty for private) and the Apple team that signs them (`TEAM_ID`) are set in `install.sh`, as in the binary's `automator.App` (`ReleaseRepo`, `PublicReleases`, `TeamID`); the release workflow refuses to sign with another team, or self-signed while `TEAM_ID` is set. While it's empty, installs and updates accept any valid signature
- **Locally**: `make package` and `make package-linux LINUX_ARCH=amd64|arm64` build the artifacts; `scripts/test-install.sh <artifact>` installs one into a throwaway home with `install.sh`, uses it and uninstalls it, files only; for an app with public releases it then installs it again from a local stand-in for GitHub's release pages (`python3`), failing if `gh` runs or a token is sent
- **Homebrew tap** in a private repository, shared with invited people; the release workflow renders the cask and formula (`scripts/homebrew.sh`, from `packaging/homebrew/`) and pushes them to the tap (`HOMEBREW_TAP_REPO`, `HOMEBREW_TAP_TOKEN`). They download through the GitHub API with `HOMEBREW_GITHUB_API_TOKEN`
  - **Cask** (`process-automator`): installs the app and links `procauto`; its postflight sets up the login items (`install-app.sh login-items`); `auto_updates`, since the app updates itself; uninstalling removes the login items, zap the data and logs
  - **Formula** (`process-automator`): installs the Linux tree and links `procauto`; its caveats give the command that sets up the scheduler's unit and the tray's autostart entry; updated with `brew upgrade`

## Installing
- **One installer**: `install-app.sh` inside the artifact installs the app it's part of. `make install`, `install.sh`, `update`, `uninstall` and the Homebrew cask all run it
  - `install [--to <path>]`: copies the app into place (beside the old one, then swapped; when that fails, the app there is left as it was and its login items, stopped for the copy, started again), links `procauto` into `BIN_DIR` (`~/.local/bin`), sets up and (re)starts the login items. Defaults (`INSTALL_DIR`): macOS `~/Applications/Process Automator.app`, Linux `~/.local/lib/process-automator`. `--to` replaces the app at that path and leaves the link alone
  - `login-items`: sets up and (re)starts the login items for the app where it is
  - `uninstall [--purge]`: stops and removes the login items, the `procauto` link (only if it points into this app) and the app; `--purge` also the data folder (config, routines, history), logs and the secrets under the build's service (the Keychain's or the keyring's: when it's locked, it says some are left and how to remove them)
  - **Login items**: macOS LaunchAgents (`<prefix>.procauto.ui`, `<prefix>.procauto.scheduler`, logging to `~/Library/Logs/process-automator/`; stopping them also stops any other copy of the app's UI, such as one macOS reopened by itself after a permission was granted); Linux the systemd user unit `procauto-scheduler.service` (logging to the journal; stopping it signals the scheduler alone, `KillMode=mixed`, as launchd does), written where systemd's user manager reads units (its `XDG_CONFIG_HOME`, which may not be the installing shell's, else `~/.config`), enabled on first install, and the tray's XDG autostart entry `~/.config/autostart/procauto-tray.desktop`, which desktop sessions start at login (never a headless one). The tray is started when one was running (again in that one's session: its environment) or when the installer runs in a desktop session (a display and a session bus), and otherwise not; replacing or uninstalling the app first stops a running tray (found by its executable) and waits up to 10 seconds for it to exit, then kills it. The paths they hold are escaped for each format (XML in the plists, systemd's quoting in the unit, the desktop entry's in the autostart entry), so a home with spaces, `&` or quotes works. Reinstalling keeps whether each starts at login (a LaunchAgent turned off is loaded and turned off again; a hidden autostart entry stays hidden). Restarting a LaunchAgent waits (up to a minute) for its old process to exit before loading it again, then tries for a few more seconds: loading it while the old one is still stopping fails. The scheduler's PATH adds `~/.local/bin` and Homebrew's to the system default. Without a systemd user session it says to start `procauto daemon` another way. The scheduler is (re)started before the menu bar app or tray, which start it when they open. On Linux it also writes the app's entry in the desktop's app menu, `$XDG_DATA_HOME/applications/procauto.desktop` (else `~/.local/share/applications/`; headless machines too): the app's name and icon (`tray/app.png`), `Categories=Utility;`, running the tray with `--open` (quoted as the autostart entry is), then runs `update-desktop-database` on that folder where it's installed (its failure ignored); uninstalling removes it. It notes when the installing shell's `XDG_CONFIG_HOME` isn't systemd's (the scheduler would read another config folder), and, outside a desktop session, when lingering is off (the scheduler then stops at logout: `loginctl enable-linger`)
  - `--files-only` (`PROCAUTO_INSTALL_FILES_ONLY=1`) writes the files but never touches launchd, systemd or the secrets store
- **`install.sh`** at the repository root and attached to every release, run from a checkout or piped (a public app's: `curl -fsSL https://github.com/<REPO>/releases/latest/download/install.sh | bash`; a private app's: `gh api repos/<REPO>/contents/install.sh -H 'Accept: application/vnd.github.raw' | bash`): checks the prerequisites, finds the latest release (or `--version`), downloads this platform's artifact and `SHA256SUMS` (public releases from GitHub's web pages, as `update` does; private ones through `gh` when it's signed in, else the GitHub API with `GH_TOKEN`/`GITHUB_TOKEN`; without those, it uses the first account `gh` is signed in to that can read the repository, the active one first, and stops naming the accounts when none can), verifies them like `update`, unpacks the artifact and runs its installer. `--from <archive>` installs a local artifact (checked against a `SHA256SUMS` beside it when there is one); `PROCAUTO_INSTALL_UNSIGNED=1` accepts any valid signature (testing local builds). When it can open a terminal (`/dev/tty`: piped from curl over ssh without one, or in an agent's shell, it can't, and asks nothing) it then offers `procauto setup`; with `--yes` it asks nothing and says to run it
- **`procauto uninstall [--purge] [--yes]`** runs the installed app's own installer; it asks first, and without a terminal it needs `--yes`. Not an MCP tool
- **Homebrew formula installs** are updated and removed with brew: `update` and `uninstall` say so instead

## Building from a checkout
- **macOS**: `make deps` (Go and the build tools, from the `Brewfile`), then `make install`: builds the core and automator-ui, assembles the `.app` with the core inside, signs it with `SIGN_IDENTITY`, and runs the installer, which stops the running core and UI, swaps the bundle and restarts them. `make uninstall` (`PURGE=1` to purge) runs the installer's uninstall
- **Stable signing identity**: development builds are signed with the same self-signed certificate (`Process Automator Dev`) on every build, with a stable bundle ID and install path, so permission grants and Keychain access survive rebuilds
- **Permissions the app may ask for**: `Info.plist` has a usage description for calendars, reminders, contacts, the camera, the microphone and Apple Events ("A plugin, program or watcher you turn on may need to …; <app> asks only when one does"), and `bundle.sh` signs the core and the app with `scripts/entitlements.plist`, the matching hardened-runtime entitlements. Linux has no equivalent: there, access is the user's (e.g. the `input` group)
- **Linux**: `make package-linux LINUX_ARCH=…`, then `install.sh --from <the tarball>`
- **The checkout is remembered** (`SOURCE_DIR`, overridable by `update.source-dir`) for updates while no published release has a download for this machine

## Update command
- **Public releases** (`install.sh` and `update` alike): read from GitHub's web pages with curl or Go's HTTP client alone: the latest release is the tag `https://github.com/<REPO>/releases/latest` redirects to (`…/releases/tag/<tag>`; with no releases it redirects to the releases page), its files are `https://github.com/<REPO>/releases/download/<tag>/<name>`, and `SHA256SUMS` lists them. Never a token, `GH_TOKEN`/`GITHUB_TOKEN` and `gh` included, and no message mentions signing in. The web address can be pointed elsewhere at build time (`RELEASE_WEB`), as the API can (`RELEASE_API`)
- **Private releases**: `update` reads them through the GitHub API, signed in with `GH_TOKEN`/`GITHUB_TOKEN` when set, else with an account the GitHub CLI is signed in to for github.com that can read the release repository: the active one if it can, else the first of the others that can (`gh auth status --json hosts`, `gh auth token --user`; each tried on the repository). When none can, it uses the active account and its error names the accounts tried; with no sign-in at all it reads unauthenticated, which a private repository refuses (the error says to sign in). Tokens are never printed. It takes the highest `vX.Y.Z` release that's neither a draft nor a pre-release
- **Newer only**: a release is installed only if it's newer than the running version
- **Verifies before running anything**: the artifact's SHA256 against the release's `SHA256SUMS`; on macOS its code signature (`codesign --verify --deep --strict`) and, given the build's `TEAM_ID`, that team's Developer ID and Apple's notarization (`spctl`). Any mismatch installs nothing
- **Replaces the app where it is**: runs the new artifact's installer with `install --to <the installed app>`, restarting the login items
- **Releases it can't read stop it**: when the releases can't be read (no access, no network), `update` says why and installs nothing
- **From a checkout**: when the releases were read and none has a download for this machine (or there are none), `update` builds the checkout's newest release tag in a temporary git worktree (the checkout itself is never touched) and installs it as above; `install.sh` says to build instead
- `--check` only reports (with a `note` on what installing involves: a download, or a build from the checkout taking minutes); `--detach` installs in the background (for frontends), logging to `update.log` and reporting the result as a notification; `--ask` says what's available (with the `note`) and asks in the terminal before installing, installing only on yes (for a frontend that can't ask itself; without a terminal it refuses); `locks/update.lock` keeps two installs from running at once
- **Progress**: the process installing records its progress in `update-progress.json` as it goes: the release, the step in words (checking, downloading, checking it's genuine, installing, or building from the checkout), the latest line the step printed, and how it ended. `update progress [--json]` reports it: `state` `installing` (the lock is held, or an update started in the last 30 seconds), `done`, `failed` (with the error; one that stopped without finishing is failed too) or `none`
- **Automatic updates** (`update.auto`, on by default; `update/auto.go`, `engine/autoupdate.go`): on each pass the scheduler asks for the latest release when an hour has passed since the last check (`update --check` counts; checks run in the background, two minutes at most) and records what it found in `update-auto.json`, with when that release was first seen. While `update.auto` is on it then decides (`update.Decide`, one rule, tested alone) whether to install it now: a newer release with a download for this machine, known for an hour, not tried automatically in the last 24 hours; nothing running or waiting its turn in run status (a run stuck past its deadline doesn't count), no enabled routine's next run within 3 minutes; not postponed; the scheduler running and the computer awake for 10 minutes since it last woke (a gap between passes), and fully awake (`sysenv.FullyAwake`: not a maintenance wake). Development builds, Homebrew formula installs and builds without `install-app.sh` are never updated by themselves (`update status`'s `automaticBlocked` says why). Otherwise it records why not (`waiting`, in words) and, when it installs, the try; then starts `update` detached with `PROCAUTO_AUTO_UPDATE=1`, which installs only a published download and records a notification either way (`update` true): installed, or that it failed and the running version keeps working. On Linux, inside a systemd service (`INVOCATION_ID`), it starts as a transient unit of its own (`systemd-run --user --collect`, its output appended to `update.log`), since restarting the scheduler's unit kills everything in its cgroup; elsewhere in a session of its own
- **`update status [--json]`**: where updates stand, with no network: `current`, `development`, `automatic` and its `setting`, `automaticBlocked`, `checkedAt` and `checkError`, `latest` and `updateAvailable`, `waiting` (the scheduler's last reason, while automatic updates are on and a newer release isn't installing) and `installing` (`installingTag`)
- **`update notes [<release>] [--json]`**: a release's notes (this version's by default; none for a development build), from the GitHub API's release by tag (`tag`, `notes` in Markdown, `url`, `publishedAt`): a public app's with no token, a private one's signed in as `update` is; kept in `release-notes/` and read again once a day, the copy kept standing in when GitHub can't be read
- **`update postpone [--json]`**: holds automatic installs back for 5 minutes (`until`; never shortening a later hold): frontends run it while they're in use

## First-run setup
- **`setup`** in a terminal walks through the steps in order, asking before each (except `auto` ones) and running the same commands as below; done steps are skipped, and it can run again any time. A choice is a numbered list, one value per line with its `enumHelp` line (the backend: recommended first), answered by number or name; anything else is asked again. `setup --json`'s `ask` lists the same lines. On `local`, it then asks for the server's URL (Enter keeps it), lists the models the server has (`GET <url>/models`) to pick by number or name, or asks for the model's name when the server doesn't answer, and asks for the server's key (`auth login local`) only when the server answers 401 or 403
- **`setup --json`** changes nothing: it lists the steps by kind, each with `done`, `optional`, `auto`, `status`, `ask` and the `commands` that do it (placeholders for my answers), for an LLM or automator-ui guiding me. An `auto` step is done without asking: whoever guides me runs its commands as soon as it comes to it

| Kind | Step |
|---|---|
| `templates` | Optional: which projects I work on (when templates are made for any), then which templates to install, with their parameters |
| `backend` | `llm.backend`, and its key or token; on `local`, not done while `llm.local.url` isn't an http(s) URL or `llm.local.model` is empty (its status names what's missing, its `ask` asks for both, and its `commands` set them, with `auth login local --browser` for a server that needs a key) |
| `usage` | While Claude Code's `/usage` can't be read (it answered without a usage report, or 3 tries in a row failed): the status line fallback |
| `mcp` | On `claude-code`: Claude Code has the app's MCP server at user scope (`mcp connect`); `auto` |
| `routine` | A routine that can't run, and why |
| `sign-in` | Each server the routines use that isn't signed in, with its `prepare` steps first |
| `turn-on` | Each routine, done once it's trusted and not paused: `routines trust <name> --yes --resume` trusts it and resumes it in one step. Untrusted, it's required; trusted but paused, it's optional (pausing a routine never makes setup unfinished) |

- **Setup is done** when every step that isn't optional is
- **Setup left shows in run status**: the scheduler checks setup on every pass and records the steps still to do (`setupLeft`), and so does every command that succeeds except the read-only ones, plus `usage` and `setup --json`, so the menu and the setup window always agree; it's written only when what's left changed; unfinished setup makes health `error`, with a reason saying what's left

## Installing through an LLM
- **`AGENTS.md`** at the repository root (where coding agents look) holds the install instructions for LLMs: check prerequisites, install (`./install.sh --yes`, or build from the checkout), then follow `setup --json` step by step, asking me each step's question (and doing `auto` steps without asking)
- **Every step runs without a terminal**: CLI commands with `--json`, and `--yes` once I've answered, the same ones the installer and `setup` use; sign-ins open my browser as they do from the CLI
