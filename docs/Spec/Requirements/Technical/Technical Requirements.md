## Core
- **Go core, one binary**: `procauto` (the Go module in `core/`, main package `core/cmd/procauto`); `core/internal/engine` is the engine (loading, readiness, runs, the scheduler, setup's steps and what each sign-in needs; Genkit for the model), `core/internal/cli` the CLI over it (commands, their output and questions), `core/internal/programs` programs (their files, the app's copies, running them), `core/internal/hooks` and `core/internal/watchers` hooks' and watchers' files (and watchers' events, polling and streaming), `core/internal/dispatch` the dispatcher that runs occurrences of any trigger, `core/internal/loginitems` starting at login (launchd, systemd and XDG autostart), `core/internal/permissions` the permissions things declare and what the scheduler found
- **A small public surface; the rest is internal**: `core/automator` (`App`, `App.Validate`, `Main`, `CheckTemplates`) and `core/pluginapi` (the plugin contract, with `pluginapi/plugintest` for plugins' tests). An app is an `automator.App` handed to `automator.Main` by its main package:

| Field | What it sets | Process Automator |
|---|---|---|
| `Name` | What people see: the app, its windows, its messages | `Process Automator` |
| `Command` | The CLI's name, and the commands messages suggest | `procauto` |
| `Folder` | The config and data folder's name, the logs folder, the release artifacts and the Linux install | `process-automator` |
| `BundlePrefix` | The prefix of the bundle ID (`<prefix>.<Command>`), which names the login items and the secrets service | `dev` |
| `ReleaseRepo`, `PublicReleases`, `TeamID` | Where `update` gets releases, whether they're public (read with no sign-in) or private (the zero value: read signed in to GitHub), and the team that must sign them | `REPO`, `PUBLIC`, `TEAM_ID` in `install.sh` |
| `Plugins` | In-process plugins compiled in | none |

- **Build values are set at link time** in `core/automator` by the Makefile: the version, the source checkout (`SOURCE_DIR`), where the templates are packaged, the release API and web address, and `BUNDLE_PREFIX` over the app's prefix
- **Another app** is a Go module that requires this one and has its own main package, plugins and templates; it builds with this repository's Makefile and scripts at the same version (see [[Spec/Requirements/Technical/Distribution|Technical: Distribution]])
- **Blank-slate engine**: the engine knows no specific service and adds no plugin; routines use the plugins the app compiles in (its `automator.App.Plugins`; procauto's is `notify`, from `core/plugins`) and the MCP servers added in config. Nothing in `core/internal/` imports a plugin; the engine runs only the list it's given
- **OS-neutral core**: OS calls live in per-OS files (`name_darwin.go`, `name_unix.go`, `name_other.go`, or a `//go:build` line), OS-bound integrations are plugins, and delivering the app's own state to the OS (its notifications, the menu bar) is the frontends' job. The one exception is the notify plugin, which shows routines' notifications itself (see [[#Plugins in `core/plugins`]]). `internal/osboundary`'s test (no `runtime.GOOS`, `syscall`, OS tools or OS paths in shared files) and `make ci`'s Linux and Windows cross-compiles enforce it
- **Config**: one YAML file, `config.yaml` in the per-user config folder (`os.UserConfigDir()/<Folder>/`: `process-automator/`), decoded strictly: unknown or retired fields are errors. It holds `mcpServers` (external servers), `plugins` (in-process plugins' own sections) and `settings`. `--config` points the CLI at another file
- **Data folder** is the config file's folder; everything the app keeps is in it:

| Path | What |
|---|---|
| `routines/` | Routine files and partials |
| `programs/<name>/` | A program: its description file and the app's copy of its executable |
| `program-data/<name>/` | A program's own folder, where its runs work |
| `hooks/<name>/` | A hook: its prompt (`hook.prompt`), or its description file (`hook.yaml`) and the app's copy of its executable |
| `hook-data/<name>/` | A program hook's own folder, where its runs work |
| `watchers/<name>/` | A watcher: its description file (`watcher.yaml`) and the app's copy of its executable |
| `watcher-data/<name>/` | A watcher's own folder, where it runs |
| `permissions.json` | What the scheduler last found of each permission, when, the latest request it took for each, and what each routine, program, hook and watcher needed then |
| `permission-requests/` | Requests to ask the OS for a permission, a file each, taken by the scheduler |
| `wake` | Written by a command that changed something, for the scheduler to make a pass at once; it removes it |
| `watcher-state.json` | Each watcher's cursor, the event IDs it has seen (7 days, at most 5000), when it last polled, started or printed an event, and why it last failed |
| `run-status.json` | Run status (frontends follow it through `status --watch`) |
| `history/<routine>/` | One record per due run |
| `notifications.json` | The app's own notifications (frontends get them through `notifications list`) |
| `memories/` | `_global.md` and `<routine>.md` |
| `trust.json` | What each routine, hook and watcher was trusted with (an LLM routine's surface, a program's checksums, a hook's trigger with its action's, a watcher's checksums; each with its permissions) |
| `plugins/<name>/` | Installed plugin folders |
| `plugin-data/<name>/` | In-process plugins' own data |
| `scheduler-state.json` | Handled slots, per routine and trigger |
| `plan-usage.json`, `statusline.json` | The Claude plan's last usage reading, and the status line the app wraps |
| `login-path` | The login shell's PATH, saved by the scheduler |
| `mcp-changes.jsonl` | Side-effecting MCP calls |
| `start.log`, `update.log` | Background runs and updates |
| `update-progress.json` | How the latest update went, or is going (`update progress`) |
| `reports/` | Readable run reports |
| `locks/`, `run.lock`, `edit.lock`, `daemon.lock`, `stop/` | Cross-process locks and stop requests |

- **Files are written atomically**, and shared state written during runs has one writer per file

## Frontends and the contract
- **The CLI is the API**: every command a frontend needs supports `--json` with a stable shape; frontends read none of the core's files (config, run status, notifications, history): only what the CLI prints. Run status comes from `status --json`, or `status --watch`, which prints it as one JSON line at once and again whenever it changes (it checks the file once a second) until stopped; the MCP server doesn't offer `--watch`, which never ends. automator-ui, the Linux tray (automator-tray) and Claude (through `mcp serve`) are frontends over it; none has its own logic or routines, and anything a frontend needs is added to the core for every frontend
- **Contract in `contracts/`**, generated from code by `make contracts` and committed; a test fails when it drifts:

| File | What |
|---|---|
| `cli.yaml` | Every command: usage, flags, the schema of its `--json` output |
| `cli/<command>.schema.json` | Each `--json` output |
| `settings.schema.json` | Every setting: type, default, limits, unit, description |
| `run-status.schema.json`, `notifications.schema.json` | The core's own files, as `status --json` and `notifications list --json` print them |
| `openapi.yaml` | Every type a frontend reads, as OpenAPI components; automator-ui generates its Swift types from it at build time |
| `examples/` | Hand-written examples both test suites check |

- **The guide** (`guide [<topic>]`, read-only) is in the binary, about a terminal screen per topic plus its generated tables: its text is written once, in `core/internal/cli/guide/<topic>.md`, and what the code defines is generated into it: the routine keys (`routines.Fields` and `settings.RoutineFields`), each backend's model providers, default model and built-in tools (`engine.Backends`, `agent.ClaudeBuiltins`, `agent.CodexBuiltins`), the inputs (worked out by `routines.Inputs`), the platforms, parameter types, outcomes, the app's plugins and `plugin.yaml`'s fields (`pluginManifest`'s `guide` tags). `--json` gives each section's text with its generated tables as data. Its examples are files tests run: the notes server is built and installed with `plugins add --dir`, and the example routine is created against it
- **Errors as JSON**: a command given `--json` that fails prints `{"error": "..."}` on stdout; checks that report their own problems (`doctor`, `routines check`, `plugins check`) print only their result
- **Edits are serialized across processes**: config and settings writes, and each whole change to routines or plugins (`edit.lock`), so concurrent frontends and tool calls never lose each other's changes or interleave a check with another's write
- **Login-shell PATH**: the scheduler resolves the user's login-shell PATH at startup and saves it (`login-path`); every command adds the saved one to its own (resolving it once when there's none and no terminal), so a command a frontend starts finds `claude`, `codex` and MCP server commands as one typed in a terminal does

## Settings
- **One registry**: every app-wide setting is declared once in `core/internal/settings/registry.go` (key, type, default, limits, unit, backend, description, and for a choice a line on each of its values: `enumHelp`); `settings list/get/set/reset`, validation, `settings.schema.json` and the settings UI derive from it. Values live under `settings:` in the config file, edited in place with comments kept
- **Types**: bool, int, number, percent, duration, cron, enum, string, path (`~/` expands), list of strings (a YAML list; comma-separated on the CLI; items optionally limited to an enum)
- **Live**: the scheduler re-reads config and settings every pass, so changes apply without a restart. A command that changes something (not one run read-only: `trust --check`, `setup --json` and `run --dry-run` are) calls `App.Changed` from the CLI's post-command hook: it records each routine's and hook's state in run status itself (paused or not, next run, why it can't be scheduled), as a pass would, so frontends show it at once, and writes the wake file (`App.Wake`) for the scheduler to act on it within about a second
- `settings list --scope app|routines|hooks`, `--routine <name>` (a hook's name too); settings for another backend show as `inactive`. A hook's settings are `hooks.<hook>.<field>` (see [[#Hooks]]) and a watcher's `watchers.<watcher>.enabled`; they're in the `hooks` scope, never the app's
- **Retired settings** (`settings.Retired`): a renamed or removed key in the config file reads as its new key (one already set wins) or not at all, and the next `settings set`/`reset` rewrites the file so. Retired: `notifications.failures` (now `runs.failure-notifications`), `notifications.on-click` (removed), `llm.openai-compat.base-url` (now `llm.local.url`). A routine's `onNotificationClick` is gone too, from settings (ignored) and routine files (an unknown field)
- **Former enum values** (`EnumAliases`): a value an enum setting no longer has reads as the one it became, wherever it's read or validated (the config file, `settings set`, a routine's or template's `automator.backends`), and shows as that; the file isn't rewritten. `llm.backend`'s `api` is `claude-api`

| Setting | Default | |
|---|---|---|
| `llm.backend` | `claude-api` | `claude-code`, `claude-api`, `local` or `codex` (both experimental, untested) |
| `llm.local.url` | `http://localhost:11434/v1` | `local`, and `claude-api`'s `local/<model>` routines |
| `llm.local.model` | empty | `local` only: the server's name for the model |
| `llm.local.keep-alive` | `1m` | `local`, and `claude-api`'s `local/<model>` routines: sent with every chat request as `keep_alive` (Ollama's extension to the OpenAI API: how long the model stays loaded after the last request from anyone); `0` unloads after each request, empty sends none. A server that answers 400 refusing the field gets the request again without it, and isn't sent it again in that process |
| `llm.usage-limit` | `90` (%) | `claude-code` only |
| `llm.budget.window` | `5h` | `claude-api` only |
| `llm.budget.window-usd` | `2` | `claude-api` only; 0 is no limit |
| `llm.budget.weekly-usd` | `20` | `claude-api` only; 0 is no limit |
| `history.retention-days` | `90` | |
| `runs.failure-notifications` | `true` | The app's own notifications for runs |
| `memories.max-chars` | `4000` | |
| `update.source-dir` | empty | The checkout `update` builds from when no release has a download for this machine |

## Routines of two kinds
- **`engine.Runnable`** is a routine as everything around a run sees it: its name, kind, file, description, source and settings, and what each kind does its own way (its settings every kind has, `RunConfig`; what keeps it from running; what checking it connects to; the sign-ins it needs; what trusting it approves; running it). An LLM routine (`engine/llm.go`) and a program (`engine/program.go`) implement it; nothing else branches on kind. The CLI type-asserts (`engine.AsRoutine`, `engine.AsProgram`) only for what one kind has: an output's per-kind section, memories, adding a program's files
- **`kind`**: `llm` or `program`. Absent means `llm` at every level: CLI flags, JSON output, MCP tool arguments, run records, trust and files. LLM routines' outputs and records are written as they were before programs, with no `kind`
- **One lookup** (`App.Find`) searches both kinds; `App.All(kinds...)` lists them, sorted by name, with the ones that don't load. A name both kinds have (files made by hand) is broken for both, saying so, until one is deleted. `App.NameTaken` refuses a taken name to `routines create`, `routines create --kind program` and `templates install`
- **`RunConfig`** (every kind): enabled, schedule, staleness, timeout, the folder runs work in, whether runs take the run queue (`Queued`), whether the usage limit holds them back (`UsesModel`), and whether a dry run needs trust (`DryRunsNeedTrust`). An LLM routine's `RoutineConfig` embeds it

## LLM routines
- **One Dotprompt file per routine**: `<data>/routines/<name>.prompt`; the file name is the routine name (lowercase letters, digits and dashes). Parsed with Dotprompt's own parser
- **Dotprompt's directory conventions**: `_<name>.prompt` files are partials (`{{> name}}`); `memories` is reserved for the app
- **Frontmatter**: plain Dotprompt (`description`, `model`, `config`, `tools` = the allowlist, `output`) plus the app's fields as Dotprompt extension fields in the `automator` namespace, written dotted (`automator.servers:`). A nested `automator:` block, an unknown `automator.*` field (`automator.permissions` among them, saying a prompt needs its plugins'), invalid YAML and an empty file are rejected; `tools` without `automator.servers`, and `automator.staleness` without `automator.schedule`, are errors
- **Each file loads independently**: a broken file is reported (`routines list`, warnings) and skipped, never taking down the others
- **Per-routine fields are declared once** (`settings.RoutineFields`: name, type, default, description, scheduled-only); parsing, validation, `settings`, the settings schema (`routines.<name>.<field>`) and `routines list --json` derive from it. Each is a frontmatter key `automator.<field>`, overridable by the setting `routines.<name>.<field>`; absent means the default

| Field | Default | Meaning |
|---|---|---|
| `enabled` | `true` | Runs on its schedule (setting only; created and installed routines start `false`) |
| `schedule` | none | Cron, local time; none means manual only. A routine without one in its file can't be given one through settings alone |
| `staleness` | `1h` | How late a missed slot may still run |
| `timeout` | `20m` | Counted from when the run starts (not while queued); the deadline is in `lastRun.deadline`; stuck at deadline + 5m |
| `effort` | `default` | `default`, `low`, `medium`, `high`, `xhigh`, `max`; Claude Code's `--effort`, Codex's `model_reasoning_effort` (same names); `claude-api` and `local` take only `default` |
| `folder` | an empty temporary folder (with `session: save`, `<data>/session-folders/<name>/`, kept) | Absolute or `~/`; must exist. Its project instructions file, the backend's own (`CLAUDE.md` on `claude-code`, `AGENTS.md` on `codex`), is added to the instructions by the core; the CLI's own loading of project files, settings and hooks is off |
| `session` | `discard` | `save` keeps the agent CLI session under an ID the core picks and gives the CLI (`claude-code`: `--session-id`; recorded when the run starts) or the CLI picks and reports (`codex`: its thread ID; recorded when the run ends). It's in `lastRun.sessionId` and history, with the folder the run worked in (`folder`) that it resumes from and the backend whose CLI resumes it (`lastRun.backend`, history's `backend`). Independent of `folder`: without one, runs work in the routine's own kept folder; dry runs never keep a session |
| `builtinTools` | `[]` | Agent CLI built-in tools, allowed explicitly, never by permission bypass, in the backend's own names: `claude-code`'s tool names (file tools stay inside the working folder); `codex`'s `shell`, `write` (the sandbox may write in the working folder), `network` (with `write`), `web_search`, `view_image`. Names the selected backend doesn't take are a problem for `doctor`, `routines check` and setup. Agent CLI backends only |
| `concurrency` | `queue` | `queue` or `parallel` |

- **Servers and tools**: `automator.servers` lists the servers the routine uses; every tool in `tools` must be offered by exactly one of them, or be named `server/tool`, one of those servers' tool, and only those tools are registered with the model. A `server/tool` naming a server not in `automator.servers`, or a tool listed twice, is an error when the file loads; an unqualified tool two of its servers offer is an error naming both qualified forms
- **Tool names the model sees**: a tool's own name, or for `server/tool`, `server__tool` with its description starting `[server]`, the same on every backend (the gateway is their one tool source). Run records' `calls` and `writes` give the routine's name (`tool`) and the server (`server`); `routines check` and the trust review give each tool's server and, when it differs, its `modelName`
- **Parameters** (`automator.parameters`: name, setting type, default, description, enum): values are per-routine settings `routines.<name>.params.<param>`, passed to the prompt as inputs; a name is lowercase letters, digits and underscores and can't shadow a built-in input; a required one without a value makes the routine unschedulable
- **Platforms** (`automator.platforms: [macos, linux]`): empty means all
- **Backends** (`automator.backends: [claude-code, codex, claude-api, local]`, `llm.backend`'s values, `api` read as `claude-api`): the backends it works with; empty means any
- **Plugin sections** (`automator.plugins.<name>`, dotted or nested) may only name in-process plugins in the routine's servers that declare they take one
- **Inputs** every routine gets: `today`, `now`, `since` (the start of the previous workday) and `trigger`, plus its parameters
- **Commands**: `routines list/show/create/update/delete/check/pause/resume/trust`, for either kind (see [[#Routines of two kinds]]); `list` and `check` without a name take `--kind llm|program|all`, default `llm`. Create never overwrites; update replaces only an existing file; both validate like loading, from `--from <file|->` or `--source`, and refuse a routine that uses a server no installed plugin or server provides, or a tool none of its servers offers (or two do), asking its servers as `routines check` does; a server that can't be asked now (not signed in yet, unreachable) leaves its tools unchecked, with a warning. A created routine's disabled setting is written before its file, so the scheduler never sees it enabled
- **`routines list --json`** gives each routine's effective settings, its folder, its schedule in words (`scheduleText`), and its model and effort as the configured backend's agent CLI takes them (`agentModel`, `agentEffort`). A program's row has `kind: program` and a `program` section (its copy, checksum, arguments, writes, secrets and whether each is stored); the LLM routine's lists are empty and its effort and session empty
- **`routines check [<name>]`** parses each file, resolves its settings, checks its folder exists, its built-in tools are the backend's, its model's provider is set up, and every server it uses (directly or through its plugins) is provided, connects its servers and confirms each allowlisted tool is offered by exactly one of them, checks the servers are signed in, and asks the local server for its models when the routine runs on it, without calling the model
- **Schedules in words** come from the core: `schedule describe <cron>` gives the words, the next few times, and the schedule as days of the week and a time when it is one (`picker`); `schedule build --days … --at HH:MM` turns those back into cron

## Programs
- **A folder per program** in `<data>/programs/<name>/`: its description file `program.yaml` as written and the app's copy of the executable it names (mode 0700). `routines create <name> --kind program --from <path>/program.yaml` resolves the executable relative to the file's folder (or absolute), refuses one that isn't a regular file with an execute bit, stages both in a hidden folder (on macOS, removing the copy's quarantine mark) and moves it into place, so a failed add changes nothing; `routines update` with a program's name does the same in place of the old copy. Only a path: `--source`, `--from -` and stdin are refused, since the executable is found beside the file. Each folder loads independently; one whose file doesn't parse or whose copy is gone is reported and skipped
- **`program.yaml`**, decoded strictly; the program's name is its folder's:

| Field | | Meaning |
|---|---|---|
| `executable` | required | The executable, relative to the file's folder or absolute |
| `writes` | required | Whether it can change anything |
| `description` | | What it does |
| `name` | | Must be the name it's added as, when given |
| `args` | | Arguments passed on every run |
| `schedule`, `staleness`, `timeout` | | As an LLM routine's, and the defaults of the same settings |
| `secrets` | | `name` (lowercase letters, digits, dashes), `env` (default: the name in capitals, dashes as underscores), `prompt` |
| `permissions` | | What the OS must allow it (see [[#Permissions]]); an unknown one is refused |

- **Settings**: `routines.<name>.enabled`, `schedule`, `staleness` and `timeout` (`settings.ProgramFields`), with defaults from its file; any other `routines.<program>.<field>` is refused, saying it's an LLM routine's setting
- **Trust** records `trust.Program`: the SHA-256 of the executable and of the description file, whether it writes and its secrets' names (for saying what changed: another executable, writes now, a secret added or dropped, a changed description file). The checksum is computed again right before it starts, and a run whose copy isn't the trusted one is refused. Dry runs need trust too. Trust is never given by the first use of trust (`InitTrust` trusts the LLM routines already there)
- **Running** (`programs.Exec`): the app's copy, in a process group of its own (`Setpgid`), with stdin empty (a hook's program: its event) and its whole environment given: `PATH` fixed per OS (`programs.DefaultPath`), `HOME`, `TMPDIR`, the desktop session's display variables the app has (`programs.DisplayEnv`: `DISPLAY`, `WAYLAND_DISPLAY`, `XAUTHORITY`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_SESSION_TYPE`, `XDG_CURRENT_DESKTOP`), its secrets under their `env` names, `PA_TRIGGER` (`schedule`, `manual`, `backfill`), `PA_FOR` (RFC 3339), `PA_RUN_ID`, and `PA_RESULT` and `PA_NOTIFY`, files in a private temporary folder. It works in `<data>/program-data/<name>/` (made on its first run). A dry run appends `--dry-run` for one that writes
- **Ending**: when the run's context ends (stop, its timeout, the scheduler stopping), the group gets SIGTERM, then SIGKILL after 5 seconds; once it exits, whatever it left in its group is killed. Its output comes through a pipe of the app's own, so a process that left the group and holds it can't keep the run going
- **Notifications** (`$PA_NOTIFY`): when it ends, each line of the file (its first 256 KiB, blank lines skipped) is a JSON object, `title`, `body`, `url`, `urgent`, `acknowledge` (no other key), made one of the app's notifications of kind `run` about the run (the program's or hook's name, `hook` for a program hook, the run's ID), at most 20 a run (`engine.NotifyLimit`). The titles recorded are the record's `notified`; a line that isn't a valid notification (bad JSON, an unknown key, `notifications.Valid`'s refusal) and how many past the limit were dropped are its `notifyProblems` and lines in the run's log; none fails the run. A dry run records none: `notified` says "would notify: <title>"
- **Outcome**: exit 0 is success, with the first line of `$PA_RESULT` (up to 500 characters) as the run's reason; another exit code fails the run with that line, or the output's last line. A secret that isn't stored is `needs-reauth`, naming the program. stdout and stderr go to the run's log and its record, their first and last 32 KiB when there's more (`programs.OutputCap`), with what was left out marked between them; the first half is logged as it comes, the last when the program ends
- **Not an LLM run**: no run queue (`Queued` false, so only its own routine lock), no usage limit, no plan-limit reading; after a sleep mid-run it runs again once only when it doesn't write
- **Sign-ins**: a program declaring secrets is a sign-in of kind `program` (`auth login <program>`), its keys `program/<name>/<secret>`, its own; a program with secrets can't take a configured server's or plugin's name. `routines delete` forgets them
- **Checks**: `doctor` and `routines check` find a secret that isn't stored or can't be read; setup has its turn-on and sign-in steps

## Hooks
- **`engine.Runnable`, with a trigger**: a hook (`engine/hook.go`) is a Runnable whose action is an LLM routine's or a program's side (`llm.go`, `program.go`) told it runs for events; it adds what it listens for, its settings and its trigger in what trust approves. Its `Kind` is its action's. `App.Hooks` lists them and `App.FindHook` finds one; `App.All` and `App.Find` never return one (Find says a hook's name is a hook's), and `App.FindAny` finds routines, programs and hooks. `App.NameTaken` refuses a name any routine, program, hook or watcher has; one made by hand twice is broken for the routine, hook or watcher until one is deleted
- **A folder per hook** in `<data>/hooks/<name>/`, added by `hooks add <name> --from <path>` (only a path: a `.prompt` file is an LLM hook, any other a program hook's description file, its executable resolved beside it and copied, staged as a program's is); `hooks update` the same in place. Each folder loads independently
- **An LLM hook's `hook.prompt`** is a routine's file parsed by `routines.ParseHook`: no `automator.schedule` or `automator.parameters`, `automator.staleness` without a schedule, and `automator.on: {watcher, type}` (required; also written dotted) and `automator.batch` (bool). Its partials are the routines folder's, `{{> memories}}` included
- **A program hook's `hook.yaml`**, decoded strictly; batch is refused (a program gets one event per run):

| Field | | Meaning |
|---|---|---|
| `executable`, `writes` | required | As a program's |
| `on` | required | `watcher` (a watcher's name) and `type` (one of the event types it declares; none: every type) |
| `description`, `name`, `args`, `secrets`, `permissions` | | As a program's; secrets are kept as `hook/<name>/<secret>` (`auth login <hook>`, a sign-in of kind `hook`) |
| `staleness`, `timeout`, `rate` | | The defaults of the same settings |

- **Settings** (`settings.HookFields`, `hooks.<hook>.<field>`): `enabled` (default true; `hooks add` writes false first), `staleness` (`10m`: how old an event may be, by its `at`), `timeout` (`20m`), `rate` (`60` runs an hour, 1 to 3600); an LLM hook also takes `effort`, `folder`, `session`, `concurrency` and `builtinTools` (`settings.HookActionFields`)
- **Watchers** (`<data>/watchers/<name>/`, `watchers add <name> --from <path>/watcher.yaml`, staged as a program's): `watcher.yaml`, decoded strictly:

| Field | | Meaning |
|---|---|---|
| `executable` | required | As a program's |
| `mode` | required | `poll` or `stream` |
| `interval`, `timeout` | | poll only: how often (default `1m`, at least `5s`) and how long one poll may take (`30s`) |
| `events` | | The events it prints, a map in its order: each type (as an event's) to its label (one line, at most 80 characters); at least one when present. Absent: any type (`watchers.Watcher.Declares`) |
| `description`, `name`, `args`, `secrets`, `permissions` | | As a program's; secrets are `watcher/<name>/<secret>` (`auth login <watcher>`, kind `watcher`) |

- **Events**: a watcher prints JSON lines on stdout: an event `{"id", "type", "at", "data"}` (`id` required, at most 256 bytes, no control characters; `type` required, `[A-Za-z0-9][A-Za-z0-9._:/-]{0,99}`; `at` RFC 3339, default when it was read; `data` an object; nothing else), or `{"cursor": "..."}` (at most 4 KiB). A line is at most 1 MiB, one poll's output 16 MiB. An event of a type its watcher doesn't declare is dropped and logged once per type (per poll, or per start of a stream); the poll still works and its cursor moves on
- **Running a watcher**: the app's copy, checked against its trusted checksum before each start, with a program's environment, `PA_CURSOR` (its saved cursor) and `PA_WATCHER`, in `<data>/watcher-data/<name>/`, its stderr in the daemon's log. A poll that exits non-zero, prints a line that's neither or runs past its timeout fails: its events and cursor are dropped. A stream's events are handled as they come, a bad line logged and skipped
- **The daemon's event side** (`engine/events.go`), in the scheduler's daemon: on every pass it starts the watchers that a hook that's on listens to (the hook enabled, trusted and with no problem but its watcher failing; the watcher trusted, `watchers.<name>.enabled` and every permission it declares granted) and stops the others, or one whose files changed. Polls run every interval by the wall clock, so one due during sleep runs on waking, after `WakeSettle`; neither a poll nor a stream starts while `sysenv.FullyAwake` is false. A stream that ends is started again: at once if it ran a minute (`streamUp`), else after a pause from a second, doubling to 5 minutes. A failed poll, or a stream ending within a minute, is the watcher's `error` in `watcher-state.json` and its hooks' problem until it works again, or a permission it needs changes
- **Each event once**: new events (IDs the watcher hasn't printed before) are marked seen, with the cursor, in `watcher-state.json` before they're handed on (at most once). Each goes to every hook listening for its type, unless it's older than the hook's staleness (dropped, logged); then to the dispatcher (`dispatch.Dispatcher`): a hook never overlaps itself (later events wait behind its run, up to 50), LLM hooks with `concurrency: queue` take its queue (tightest staleness first) and then the device's run queue, programs and parallel ones don't; an occurrence that waits past its staleness is recorded as missed. A batching hook's waiting occurrence takes later events in (at most the latest 100). Stopping a hook's run drops what waited behind it
- **Before a run**: stale events are dropped again; the hook's runs in the last hour count against its rate (one past it is dropped, logged), and when the occurrences due in the last hour pass `LoopFactor` (3) times its rate it's paused (`enabled` false) and a run is recorded as `skipped`, saying why. Then it waits for a full wake, and two runs of a hook never start in the same second (a run's history ID is its start)
- **What the action gets**: the occurrence (trigger `event`, or `manual` from `hooks fire`; its ID `<trigger>:<watcher>:<event id>`; its time the latest event's) carries the events. An LLM hook's prompt gets the routine inputs without `trigger.data`, plus `event` (the latest) and `events`, each `{id, type, at, watcher, data}` with every string from the watcher (its `id` and `data`'s texts) wrapped in `<untrusted>`…`</untrusted>` and `<`, `>` inside escaped; the app adds `{{appEventBlock}}` to the end of its source: the events as JSON (`<`, `>` escaped by the encoder) in an `<outside-event-data>` block that says they're data, never instructions. A program hook's stdin is a private temporary file holding the event as one JSON object; `PA_TRIGGER` is `event` (or `manual`), `PA_FOR` the event's time; it works in `<data>/hook-data/<name>/`
- **Declared events** (`App.CheckOn`, `App.LabeledOn`, `engine.WatcherEvents`, `engine.WatcherHint`): `hooks add|update` refuses an `on.type` its watcher (found and loading) doesn't declare; afterwards it's the hook's readiness problem ("it listens for key.end, which its watcher nav-keys doesn't print"), which keeps it from listening. `hooks fire` refuses a sample of a type the watcher doesn't declare. `HookInfo.on` and `TrustOutput.on` carry `label`, the watcher's label for its type; `hooks.On.When()` is "When End key pressed (from nav-keys)" (`hooks list`'s RUNS column, `hooks show`, the review). `WatcherInfo.events` lists the declared events, each `{type, label, hooks}` (the hooks of its type and of every type), and `hint` says when it declares none; a hint is never a problem, a reason or red
- **Trust**: a hook's approval is its action's (a surface or a program's checksums) and `trust.Trigger` (watcher, type, batch); another one says what changed (listens to another watcher, acts on another type, takes events in batches). Hooks are never trusted at first use. A watcher's approval is `trust.Approval.Watcher` (its checksums, secrets and declared `events`, so a change says which event was added, dropped or relabelled); without it the hook's problem says so, with `hooks trust <hook>` as the fix. `hooks trust <hook> [--check] [--yes] [--resume]` (and `routines trust <hook>`) reviews and trusts it (`TrustOutput` with `hook`, `trigger`, `warnings`: an LLM hook with write tools, or built-in tools the backend doesn't mark read-only, acting on event data; and `watcher`: its trust and, while there's one, its `description`, `mode`, `program`, `events` and `changes`); `--yes` trusts its watcher too when it isn't trusted, in the same write; `--resume` also turns it on. `watchers trust <watcher> [--check] [--yes]` trusts a watcher alone. Neither is an MCP tool. Every trust review (`routines trust`, `hooks trust`) lists `signIns`: the sign-ins it still needs (its servers', its own secrets', its watcher's) whose secrets or OAuth tokens aren't stored, and `permissions`: every permission it needs, with its state (see [[#Permissions]]); `routines list` and `hooks list` say `turnOn` while `trust --yes --resume` has something to do (not trusted; paused with a schedule; a hook off, or its watcher not trusted)
- **Commands**: `hooks list|show|add|update|delete|trust|pause|resume|fire`, `watchers list|show|add|update|delete|trust|pause|resume` (`--json`: `HookInfo`, `HookDetail`, `HookChange`, `WatcherInfo`, `WatcherDetail`, `WatcherChange`, `WatcherTrustOutput`). `hooks fire <hook> [--event <path|->] [--event-json <json>] [--dry-run]` reads a sample event as a watcher's line (a file, stdin or the flag; `--event` isn't an MCP argument, `--event-json` goes on stdin) and runs it through `App.Fire`, whatever its staleness and rate, printing `RunOutput`. `run`, `start`, `routines show` and `routines check` refuse a hook's name; `routines pause|resume` (`RoutineChange.hook`) and `stop` take one
- **Run status and checks**: hooks are `hooks` in `run-status.json`, apart from `routines` (see [[#Run status and health]]); `doctor` checks each hook that's on (area `hook`); setup has no hook steps

## Templates
- **Files shipped with the app**, never compiled in: `Contents/Resources/templates` in the `.app`, `share/<Folder>/templates` in the Linux tree, the checkout's `templates/` in development builds; `paths` shows the folder. An empty or missing folder lists none; the repository's `templates/` holds only a README
- **Checked like the app's own**: every template loads as a routine, includes `{{> memories}}`, and renders with the standard inputs, anchored in `today` or `since`, with no template syntax left (`automator.CheckTemplates`, run by the tests on the shipped folder)
- **Tags are folders**, general to specific; `projects/<project>/…` makes a template that project's (`project` in `templates list`). Installing copies a template flat into the routines folder
- `templates list [--all]` shows the ones for this OS (tags, project, parameters, platforms, backends, whether it supports the selected backend (`supportsBackend`), installed or not); `templates install <tags>/<name> [--as <name>] [--set param=value]` refuses a template that doesn't support the selected `llm.backend` (saying how to switch), validates every value first, never overwrites a routine, stores values as `routines.<name>.params.<param>`, prints the template's description, and leaves the routine disabled and untrusted

## Model backends
- **`llm.backend`** picks the loop behind one `Backend` interface:
  - `claude-api`: Genkit runs the loop, routed by the model's provider: `anthropic/<model>` against the Anthropic API with the key stored by `auth login anthropic`; `local/<model>` on the local server (as on `local`). Only the providers set up are registered. Any other provider, or a model with no provider, is a problem; a routine with no model fails its run, saying so (the backend has no default)
  - **`claude-api` readiness**: the backend needs an Anthropic key unless every routine's model is `local/…` (with no routines it does). Each routine's model needs its provider set up: a key for `anthropic/…`, an http(s) URL for `local/…`; otherwise it's a problem for that routine (`doctor`, `routines check`, setup, the scheduler)
  - `local` (experimental, untested: its description, setup's status and the installing agent's instructions say so): Genkit runs the loop on the local server, every routine on `llm.local.model` whatever its `model` names, unless that's `local/<model>`, another model on the same server. Ready when `llm.local.url` is an http(s) URL and `llm.local.model` is set; each routine needs a model to run on. No Anthropic key is involved
  - **The local server** (`local`, and `claude-api`'s `local/<model>` routines): one OpenAI-compatible server's Chat Completions API through Genkit's `compat_oai` plugin, at `llm.local.url`, with the key stored by `auth login local` as a bearer token when there is one (none is sent otherwise, and `OPENAI_API_KEY` from the environment never is). A tool error, input that doesn't fit a tool's schema or a call to a tool that doesn't exist goes back to the model; a server that isn't answering or answers with an error fails the run, saying which. `doctor` and `routines check` ask it for its models (`GET <url>/models`, 3 s timeout): not answering, refusing the key, no API there (404), or not listing the model (a model without a tag matches Ollama's `:latest`) is a problem. The scheduler and `setup --json` never connect to it; the interactive setup does, to list its models
  - **Former names**: `openai-compat/<model>` is `local/<model>`; `auth login|logout openai-compat` is `local`; a key stored under the former `openai-compat` name is read when `local`'s isn't stored, and `auth logout local` deletes both
  - `claude-code`: headless Claude Code (`claude -p`) on the user's Claude plan, signed in through Claude Code itself or a `claude setup-token` token stored by `auth login claude-code`
  - `codex` (experimental, untested: its description and setup's status say so): headless OpenAI Codex CLI (`codex exec`) on the user's Codex sign-in (`codex login`: a ChatGPT plan or an OpenAI API key), read from `$CODEX_HOME/auth.json`. Ready when `codex` is found (on the login-shell PATH) and `codex login status` (no network) says it's signed in, checked at most once a minute; `auth login codex` says to run `codex login`
- **Agent CLI backends** are one generic `CLI` backend plus a small `CLITool` per CLI (how to start it headless and isolated, its MCP config, environment and model naming, and how to read its result); a test keeps them in step with the CLI's backend list and the `llm.backend` values
- **Shared by both**: Dotprompt rendering through Genkit (inputs, partials, memories) and the tool gateway (allowlist, call log, dry-run interception). For agent CLIs, the gateway's tools are served over a loopback MCP server guarded by a random bearer token, named `procauto`
- **Claude Code is isolated** from the user's own setup: `--tools` limited to the routine's built-in tools (none by default), `--strict-mcp-config`, `--permission-mode dontAsk`, `--setting-sources ""`, `--restricted`, `--disable-slash-commands`, `--no-chrome`, a replaced system prompt, a capped number of turns, and `--no-session-persistence` unless the session is saved. `ANTHROPIC_API_KEY` and other inherited credentials are stripped; `CLAUDE_CODE_DISABLE_AUTO_MEMORY` and `CLAUDE_CODE_DISABLE_ORG_MEMORY` are set
- **With `claude-code`** only `model` from the frontmatter applies; `config` is ignored, and only Claude models run
- **Codex is isolated** from the user's own setup as far as Codex allows: `--ignore-user-config` (no `config.toml`: no MCP servers, profiles, model or provider settings of mine; so no project is trusted and the folder's `.codex/` config, hooks and rules stay off), `--ignore-rules`, `--skip-git-repo-check`, `--ephemeral` unless the session is saved, and `--config` overrides: `approval_policy="never"` (nothing asks; what would need an approval is refused), `developer_instructions` (the routine's system prompt and the folder's `AGENTS.md`; Codex's own base instructions stay), `project_doc_max_bytes=0`, `history.persistence="none"`, `check_for_update_on_startup=false`, `analytics.enabled=false`, Codex's apps, plugins, tool suggestions, subagents, image generation, browser and computer use, memories, goals and hooks off, skills' instructions off, and its question tool (`request_user_input`) off. Codex's global `AGENTS.md` in `CODEX_HOME` still loads. `CODEX_API_KEY` and `OPENAI_API_KEY` are stripped from its environment
- **One call to the app's tools may run an hour** on both agent CLIs (Claude Code's `--mcp-config` server `timeout`, Codex's `tool_timeout_sec`; `agent.toolCallTimeout`): their own limits, about a minute by default, would cut off a slow plugin call (a script's first `git fetch` of the day) long before the routine's timeout, which is what ends a run
- **Codex's tools**: the routine's MCP server is its only one (`mcp_servers.procauto`: `url`, the bearer token through `bearer_token_env_var` from the environment, never the command line; `required = true`, so a run that can't reach it fails, saying its tools couldn't be reached; `default_tools_approval_mode = "approve"`, so the gateway alone decides; `omit_tools_from = ["deferred"]`, so its tools are in the model's tool list (as `mcp__procauto` tools) rather than found through Codex's `tool_search`; a one-hour tool timeout). Its shell (`features.shell_tool`), web search (`web_search` `live` or `disabled`) and image viewing (`features.view_image`) are on only when `builtinTools` names them. The sandbox is `read-only` unless `builtinTools` has `write` (`workspace-write`, with network access only with `network`). Its file-editing tool comes with the model and can't be turned off: the read-only sandbox refuses its writes. A dry run drops `write` and `network`: a read-only sandbox, no network
- **With `codex`** only `model` from the frontmatter applies: `openai/<id>` (or a bare ID) is `--model <id>`, none is Codex's default, any other provider's model is an error. There's no turn limit (the routine's timeout bounds a run). Its result is read from the `--json` events: the thread ID (`thread.started`), the last `agent_message`, tokens (`turn.completed`: the run's total across its model calls); a non-zero exit, a `turn.failed`, a turn that never completed or no final message fails the run (with the turn's error, the last `error` event, or stderr); a usage limit or a missing sign-in is said so
- **Keep awake**: every run holds off the computer sleeping on its own until it finishes: on macOS `caffeinate -i`, tied to the process; on Linux a logind inhibitor (a file descriptor), `sleep:idle` when allowed, otherwise `idle`. A closed lid still sleeps
- **Sleep and wake**: sleep is detected without OS calls, as wall-clock time that passed while Go's monotonic clock (stopped during sleep on macOS and Linux) didn't. After the computer wakes, the scheduler waits 15 seconds for the network before starting runs. On macOS a scheduled run doesn't start in a maintenance wake (`System Capabilities` in `ioreg` without the graphics bit), but waits for a full wake; Linux has no maintenance wakes that run apps. A run that failed after the computer slept during it runs again once, when it made no writes, has no agent CLI built-in tools and didn't fail on a sign-in or the plan's limit

## Runs
- **Occurrences**: every run carries what triggered it: kind (`schedule`, `manual`, `backfill`, `event`), a unique ID, the time it's for, optional data (a hook's events). Routines get it as the `trigger` input, and `today`/`since`/`now` are computed from its time (a scheduled run's `now` is its slot). Run status (`lastRun.trigger`, `lastRun.for`) and history (`trigger`, `triggerId`, `for`) record it
- **Backfill**: `run <routine> --date YYYY-MM-DD` runs as of that day (today or earlier): at the routine's first scheduled time that day, or the current time of day if it has none. Works with `--dry-run`, recorded with trigger `backfill`, never touches scheduler state
- **`run`** runs in the terminal and prints the reply (`--json`: `RunOutput`, the agent's result with its fields at the top level, or for a program `kind` and its `program` section, so none of the agent's fields is required); **`start`** runs detached and returns at once, logging to `start.log`, followed through run status and history
- **Outcome**, strongest first:
  1. a backend error (model or CLI error, max turns, timeout): `failed`
  2. a sign-in failing mid-run: `needs-reauth`
  3. a write tool whose last attempt failed: `failed`, whatever the model says (a retry that succeeds is fine)
  4. the routine's own report through the built-in `report_outcome` tool (`done`, `nothing_to_do`, `failed` + reason), which both backends tell the model to call. `failed`, or no report at all, fails the run; `nothing_to_do` is a success with its reason
- **Tool errors go back to the model** inside the loop; rules 2 and 3 turn an unrecovered one into a failed run. A source that can't be read is an error, never an empty result
- **Structured results**: a routine may declare a Dotprompt `output:` schema; the agent requests that shape (Genkit output schema; `claude -p --json-schema`; `codex exec --output-schema` with a file in the run's private temporary folder, in the strict form Codex asks the model for: every property required, optional ones nullable (Picoschema's optional fields reduced to their alternatives), no others; the nulls are dropped again), validates it (a missing or invalid result fails the run) and stores it in history as the run's `output`, next to the text. A valid result without a reported outcome counts as done; a reported outcome still decides
- **History**: every due run leaves a record in `history/<routine>/` (executed, couldn't start, missed, interrupted, stopped) with outcome, reason and, by kind, its section: an LLM routine's `result` (inputs, tool calls and writes with their errors, tokens, cost with `claude-api`, the final text), a program's `program` (exit code, summary, output, checksum) and `kind: program`; a hook's run has `hook: true` and its `events`. Dry runs leave none. `runs [<routine>] [--since 7d|<date>] [--limit N]` lists them; `runs show <id> [--open]` shows one in full, or as a readable report. Pruned by `history.retention-days`
- **Queue and concurrency**:
  - `queue` routines, scheduled or run by hand, take a device-wide cross-process queue lock: one at a time, tightest staleness first, staleness re-checked before each. `parallel` routines and programs never take it
  - A run waiting for its turn (the queue, or its own routine's previous run) is `queued` (with `queuedAt`); only `running` counts for `busy`, the timeout and the stuck limit. Waiting is polled, so it can be stopped. A routine never overlaps itself: a slot due while it's still running waits (and is missed past its staleness)
  - OAuth refresh takes a per-credential cross-process lock around refresh-and-save, re-reading the token first and refreshing only if it's still stale
- **Stopping**: `stop <routine>` stops its run, running or queued, in whichever process runs it (a stop request the run picks up within a second), waits for it to end, and records it as `stopped`
- **Dry runs** (`--dry-run`) intercept every tool not declared read-only by its server (MCP `readOnlyHint`), returning what the write would have sent, and get only the read-only built-in tools (Read, Glob, Grep, WebSearch, WebFetch)
- **`mcp call <server> <tool> [json-args]`** calls one tool outside any routine, for debugging (writes run for real); `mcp tools <server>` lists a server's tools

## Scheduler
- **`procauto daemon`** runs the scheduler, started at login and kept alive by the OS (a LaunchAgent with `KeepAlive`, or a systemd user unit); the OS does no scheduling
- **Every 30s** it re-reads config, settings and routine files and runs what's due, and starts or stops the watchers hooks listen to (see [[#Hooks]]); it heartbeats run status every 10s (`validUntil` = now + 60s)
- **At once when woken** (`engine/wake.go`): it looks for the `wake` file every 250 ms (`WakePoll`), removes it and makes a pass then (the same pass: permissions, run status, slots, watchers), so a hook turned on hears its watcher, and one paused stops it, within about a second. A start removes a wake left from before (its first pass covers it). A hook it pauses for its rate, and the OS's answer to a permission request, make a pass too
- **Slots**: the most recent unhandled slot of each routine is due; older than its staleness, it's recorded as `missed`, not run; only the latest slot counts after a long outage. Slots are marked handled before running (at most once). On first start only a slot within its staleness runs, and nothing is reported missed
- **Scheduler state** is kept per routine and per trigger (`scheduler-state.json`: a time for cron slots)
- **Queued routines** go to an in-process worker and parallel ones start on their own, so the scheduler never waits for runs. Shutdown cancels and records in-flight runs; runs found still `running` or `queued` at start were cut off and are failed as interrupted
- **Nothing only logged**: a routine it can't load at its slot is a failed run, a missed slot a missed run, and a scheduler that can't work at all (e.g. the config doesn't load) sets a `problem` in run status until it works again
- **Logs**: macOS `~/Library/Logs/process-automator/scheduler.log`; Linux the journal

## Run status and health
- **`run-status.json`** is the single record frontends read: `health` (`ok`, `error`, `none`), `busy`, `summary`, `reasons`, `setupLeft`, `pendingAcknowledgements` (how many notifications wait to be acknowledged; absent when none) and `waiting` (those, oldest first: `id`, `title`; any makes health `error`, with one reason, after setup's and before any routine's: `acknowledge` true, its text "(1) Acknowledgement pending" or "(N) Acknowledgements pending", its detail their titles, a line each), `problem`, `validUntil` (setup's reason, while `setupLeft` isn't empty, has `setup` true: choosing it opens setup), and per routine `enabled`, `problem`, `turnOn` (all that keeps it from running is that it, or its watcher, isn't trusted: setup lists it as a turn-on step, so it's no reason of its own, and its summary is "Needs turning on"), `nextRunAt`, `lastRun` (trigger, for, ID, session ID, folder, backend, started, finished, deadline, queued, outcome, reason), its own `health` and `summary`, and `healthResetAt`. Hooks are in `hooks`, never in `routines`, with the same fields and `watcher`, the watcher it listens to (a hook's `problem` is why it can't run while it's on, ending with what's wrong with its watcher, "its watcher " and `watcherProblem`, which says it about the watcher: failing, untrusted, paused, a permission only it needs; its summary says "Waiting for events" when there's nothing else to say). Schema in `contracts/run-status.schema.json`
- **The core decides health**: a routine is unhealthy when its last run failed, needed a sign-in, was missed or skipped, when it can't be scheduled, when a slot wasn't picked up within 2 minutes, or when a run is past its timeout + 5 minutes (25 minutes without a deadline). Unfinished setup and a scheduler problem also make health `error`. `stopped` and `queued` don't. A last run that started before `healthResetAt` (and isn't still running or queued) doesn't count: until it runs again, its own `health` is `none` and its summary starts "Permissions changed; "
- **Reasons**: a short headline per problem with a `detail` and the run it's about, computed by the same rules as `health`; `hook: true` when it's about a hook. Enabled hooks count for health and `busy` as routines do. A `watcherProblem` is one reason for the watcher, whatever the number of enabled hooks on it, with `watcher` set: `watcherProblem` and the hooks that listen ("home-key is failing: … (home-joke and say-hi listen to it)"); each hook's own reason says only what else is wrong with it
- **Busy** is set while a routine is `running`

## Plugins
- **External plugins** are `mcpServers.<name>` entries: a local `command` (`args`, `env`, `dir`) or a remote `url` (`transport`: `streamable` or `sse`; `auth`: `oauth` (default), `headers` or `none`; `headers`; `scopes`; `oauthClient` with `clientIdKey`, `clientSecretKey`, `redirectPort` for servers without dynamic client registration), plus `description` and `permissions` (`config.Server`: the spec and its permissions; `Config.Permissions` has every entry the file defines). Local servers that issue their own credential on first contact set `pairing`
- **Secrets are only referenced**: `{secret-key}` in `env` or `headers`; `auth login/logout/status` derive what to ask for from the spec, so a server needs no code. These keys are global: servers may share one. An in-process plugin's declared secrets are kept under `plugin/<name>/<secret>`, its own
- **Accounts** are `accounts.<name>.of: <plugin>` entries (`plugins add <name> --account-of <plugin>`): the plugin (compiled in, in-process or external, or an `mcpServers` entry) under the account's name, resolved when config loads (`engine.Load`), with its description, `Prepare`, permissions and tools. An external one's server is its plugin's current spec (a config override of a preset included) with every key it references, in `env`, `headers` and `oauthClient`, read under `account/<name>/<key>` instead (`config.AccountSpec`); its OAuth tokens (`oauth/<name>`), an in-process one's secrets (`plugin/<name>/<secret>`), data folder and routine section are per name already. An in-process account reads its own `plugins.<name>` section, or its plugin's while it has none. Not taken: an account named like a plugin, server or account, of a name that's none, of another account (the error names the plugin to use), or of a plugin with nothing to sign in to. `plugins list` and `auth status` (`accountOf`) and setup's sign-in step say which plugin it's an account of. `plugins remove <account>` deletes the entry and forgets all its credentials, its own app's client ID and secret too, never its plugin's; an added server with accounts isn't removed until they are
- **The plugin convention**: MCP plus every tool declaring annotations with `readOnlyHint`; a tool not marked read-only is a write
- **`plugins add <name>`** (`--url` or `--command` with `--arg`/`--env`, `--auth`, `--transport`, `--header`, `--scope`, `--description`, `--permission`, or `--dir`; `--replace`) writes the server to `mcpServers`, validated like config loading. Plugin names are lowercase letters, digits and dashes; local commands are absolute paths or names on PATH. `plugins remove` deletes it from config, then its installed folder and its credentials, keeping secrets another server still references
- **Trial**: `plugins add` starts the server, does the handshake and lists its tools before writing anything. Rejected if it doesn't answer within 90s, offers no tools, lists a tool twice, or has a non-object input schema; plugin folders also need annotations on every tool (a warning for other servers). It reports each tool as read-only or write. A server needing credentials is tried as far as possible (a remote one must at least answer HTTP); `plugins check [<name>]` runs the full trial after sign-in. The trial runs the server unsandboxed, under the approval `plugins add` already needs
- **Plugin folders**: `plugins add <name> --dir <folder>` copies a folder with a `plugin.yaml` (`command`, `args`, `env`, `description`, `pairing`, `permissions`) to `<data>/plugins/<name>/`, trying the staged copy before moving it into place; relative commands resolve inside it, and neither the command nor any symlink in the folder may point outside it. `--replace` keeps the old copy if the new one fails
- **Plugins compiled in** (`core/pluginapi`, public, a leaf package with no engine dependencies): a `Plugin` is a name, a description, `Prepare` (steps done outside the app before its first sign-in), `Permissions` (what the OS must allow it; a config entry replacing an `External` preset declares its own) and either `External` (a preset server spec, replaced by a config `mcpServers.<name>` of the same name) or `InProcess`: `Serve` (builds the MCP server), the `Secrets` it declares, `RoutineSection` (it reads a section from the routines that use it) and the servers it `Uses`. An in-process plugin's `Host` gives `Connect` (another server), `ConnectApp` (the app's own MCP server, read-only: `<this executable> --config <config> mcp serve --read-only` over stdio), `AppName()` (the app's name, e.g. a notification's sender), `Config` (its `plugins.<name>` section, strict), `Secret` (only those it declares), `DataDir()` (`<data>/plugin-data/<name>/`), `RoutineConfig(v)` (the running routine's section, strict), `Run()` (the routine, its run's history ID and folder) and `Notify(Notice)` (a notification, its title, body, link, urgency and whether it waits to be acknowledged, handed to the app as its own, about the run; it returns its ID). A host is made per session; outside a run, the routine parts are empty. A config `mcpServers.<name>` that clashes with an in-process plugin's name is an error. The rest of the contract (validating specs and plugins, secret references) is the engine's, in `internal/`. `pluginapi` also has `CallJSON` and `ResultText` for calling another server's tools, and `pluginapi/plugintest` a fake `Host` and an in-memory session for plugins' tests
- **Plugin names** are lowercase letters, digits and dashes, as are an in-process plugin's secret names; an app's plugins are checked once, when `automator.Main` starts (`App.Validate`, which an app's tests also run)
- **`plugins list`** shows every server routines can use; `mcp tools <server> [--json]` its tools, marking read-only ones

## Plugins in `core/plugins`
- **`notify`** (`core/plugins/notify`, built only on `pluginapi`, in an app only if its `Plugins` list it; procauto's do), declaring `notifications`. `notify_me(title, body?, url?, urgent?, acknowledge?)`, a write tool (dry runs intercept it) that hands every notification to the app (`Host.Notify`), which records it about the run and shows it through the frontends; it says so with the notification's ID. A click opens its `url`, else the run. It has no settings. With `acknowledge`, a body is required and may be long (a whole report). The call is in the run's history like any tool call; nothing else is kept
  - **macOS**: UserNotifications, from a darwin-only cgo file (`deliver_darwin.go`, built `darwin && cgo`; the core is built with `MACOSX_DEPLOYMENT_TARGET=14.0`). The core runs from inside the app's bundle and is signed with the app's bundle ID as its identifier, so its notifications are the app's and share its permission; if macOS hasn't been asked, the first one asks. Outside an app bundle (a development build) it reports that it can't notify rather than calling UserNotifications. `urgent` is time-sensitive
  - **Linux**: the freedesktop notification service (`org.freedesktop.Notifications.Notify`) on the session bus, in pure Go (godbus), as the app's name; `urgent` is critical urgency. Linux builds stay CGO-free
  - **Other OSes** (and macOS without cgo): `notify_me` fails, saying it isn't supported
  - **Tests** replace the OS call (`notify.Deliver`) and never show a notification

## Permissions
- **The set** (`permissions.All`): `input-monitoring`, `accessibility`, `screen-recording`, `notifications`, `full-disk-access`, `calendars`, `contacts`, `reminders`, `microphone`, `camera`, `automation`; `permissions.Check` refuses any other, wherever one is declared, and keeps them sorted, each once
- **Declared by what runs code**: a plugin folder's `plugin.yaml` and a config server's `permissions` (`plugins add --permission`), a compiled-in plugin's `pluginapi.Plugin.Permissions` (checked by `App.Validate`), and `permissions` in `program.yaml`, `hook.yaml` and `watcher.yaml` (`programs.Spec`). `App.ServerPermissions` is a server's: its config entry's, else its plugin's
- **What needs what** (`Runnable.needs`, `App.Permissions`, `App.WatcherPermissions`): an LLM routine or LLM hook, the permissions of every server it reaches (`App.Servers`, plugins' `Uses` followed); a program or program hook, its own; a hook, its action's and its watcher's. Each is an `engine.PermissionNeed`: `permission`, `label`, `state`, `by` (each `{kind: plugin|program|hook|watcher, name}`), `where` (following "turn it on") and `settingsUrl`
- **Checked by the daemon** (`App.RecordPermissions`, at the start of every pass, before anything is judged): every permission in the set, through `sysenv.CheckPermission` in a fresh child process (the app's binary with `PA_PERMISSIONS_PROBE` set prints them as JSON and exits, before `automator.Main` does anything else; when it can't answer, the daemon checks itself), written to `permissions.json` (`checkedAt` and a status each). Everything else reads it (`App.PermissionState`): nothing recorded is `not-checked`. States: `granted`, `missing` (turned off or never asked), `unknown` (no way to check it here), `unsupported` (not on this OS), `not-checked`; only `missing` keeps anything from running (the daemon checks before it schedules or starts anything, so it never acts on `not-checked`, and a CLI refreshing run status before the first check doesn't turn health red)
- **A change resets health**: the same write records, by name, what each routine, program, hook and watcher needs, with each permission's status (`needs`). One whose entry differs from the last check's (a status, or which permissions) gets `healthResetAt` in run status (`runstatus.ResetHealth`) and, for a watcher, its `error` cleared in `watcher-state.json`, before run status is brought up to date in that pass; so does the check after a `permissions request`. The first check that records `needs`, and names new since the last, reset nothing. History isn't touched
- **The checks** (`core/internal/sysenv`, per-OS files):
  - **macOS** (`permcheck_darwin.go`, `darwin && cgo`): `IOHIDCheckAccess` (listen events), `AXIsProcessTrusted`, `CGPreflightScreenCaptureAccess`, UserNotifications' authorization status (inside the app's bundle; outside it, `unknown`), EventKit's (full access) for calendars and reminders, Contacts', and AVFoundation's for the microphone and camera. Full disk access and automation have no public check: `unknown`. None shows a prompt. Without cgo, every one is `unknown`. `sysenv.PermissionPane` gives each its System Settings page as an `x-apple.systempreferences:` address
  - **Linux**: `input-monitoring` is read access to any `/dev/input/event*` (none there: `unknown`); the others are `unsupported`; nothing to ask, and `where` says to join the input group
  - **Other OSes**: `unsupported`
- **A readiness problem**: `Assess` adds one for each need that blocks (`PermissionProblems`): its text names what needs it and the permission; its `Fix` is `permissions request <permission>` and where it's turned on (not checked: starting the scheduler); `Problem.Permission` carries the permission and, when it isn't granted, `Problem.Open` its address. A routine that has one isn't scheduled (setup's step to fix it runs `permissions request <permission>`), a hook's is its run-status problem, and a hook whose action has one isn't a listener; a watcher with one isn't started
- **Trust**: `trust.Approval.Permissions` (an LLM routine's, its servers'; a program's or a watcher's, its file's; a hook's, its action's), always written (`[]` for none). Another set is a change ("needs the X permission now", "no longer needs the X permission"). A record written before permissions existed has none (`Record.Unrecorded`) and covers whatever it needs until `InitTrust` records them (`trust.Store.RecordPermissions`), once
- **Asking** (`App.RequestPermission`, `permissions request <permission>`): only while run status is fresh (the daemon runs), it writes `permission-requests/<permission>` and waits up to 10 s for the daemon to take it, then up to 3 s for its answer. The daemon (`servePermissionRequests`, every 500 ms) takes it, records in `permissions.json`'s `requests` whether it can ask (`sysenv.CanRequestPermission`: `IOHIDRequestAccess`, `AXIsProcessTrustedWithOptions` with its prompt, `CGRequestScreenCaptureAccess`, UserNotifications inside the bundle, EventKit, Contacts and AVFoundation only when the app's `Info.plist` has their usage description, which it has; never full disk access or automation), asks (waiting up to 2 minutes for an answer given in a handler), then checks every permission again, brings run status up to date and makes a pass. Meanwhile it follows the permission (`follower`): every 2 s for 3 minutes it checks it in a fresh child process, and once it differs from what was recorded (turned on in the OS's settings, where a request often sends me) makes a pass at once. `PermissionRequest` is the need plus `asked` and `why`
- **Commands**: `permissions list [--all]` (`PermissionReport`: `checkedAt` and each permission something needs, or every one, with what needs it: `neededBy`, each `{kind: routine|program|hook|watcher, name, enabled, by}`), read-only; `permissions request <permission>`, not read-only. Outputs carry `permissions`: `routines list|show`, `hooks list|show`, `watchers list|show`, `routines trust`, `hooks trust` and `watchers trust`; `plugins list` the names each plugin declares

## Sign-ins and secrets
- **`auth login <server|anthropic|claude-code>`** (`codex` signs in with `codex login`, outside the app): OAuth in the browser for remote servers (dynamic client registration or the server's `oauthClient`, PKCE, rotating refresh tokens persisted); keys and tokens typed in the terminal, or on a short-lived local page with `--browser`. A plugin with `Prepare` steps shows them and waits for me to say they're done before asking for anything. Web addresses and Markdown links (`[text](https://…)`) in the steps are links on the secret page and in the Setup window; the terminal shows a Markdown link as its text and address. `auth logout` forgets a server's credentials; `auth status` shows which are stored
- **Unattended refresh**: a run never opens a browser; an expired or revoked credential is a distinct `needs-reauth` outcome naming the server
- **Secrets store** behind `secrets.Store`: the macOS Keychain through `/usr/bin/security`, and the Secret Service (GNOME Keyring, KWallet) through `secret-tool` on Linux; one item per key under the build's service (`dev.procauto` from the Makefile's default prefix, `process-automator` for a plain `go build`), values written on stdin (never argv) and base64-encoded; values stored by hand are read as-is. Without `secret-tool`, nothing is found and storing says what to install. A secret in a locked keyring that can't be unlocked (no prompt can show, or it's dismissed) is an error saying the keyring is locked, never "not found"; secret-tool's errors say the keyring must be running and unlocked. On both OSes, a secret that can't be read (a locked Keychain or keyring) is never taken for one that isn't stored (`secrets.Lookup`): readiness, a routine's model problem and runs say it can't be read, and `auth status` shows it as the row's `problem`
- **Never in config**: secrets live only in the store

## Notifications
- **The app's own**, recorded by the core in `notifications.json` next to run status (schema in `contracts/notifications.schema.json`), by `kind`: runs that failed, needed a sign-in, were missed or skipped (`failure`, unless `runs.failure-notifications` is off) and update results (`app`), and those a routine or hook asks the app for in its run (`run`: a plugin's through `Host.Notify`, a program's through `$PA_NOTIFY`; `routine`, `run` and `hook` say whose; `urgent`; `url`, a link; `acknowledge`). Only kind `run` has a `url` or waits; `notifications.Valid` refuses one with no title, one to acknowledge with no body, and a `url` that isn't an http or https link with a host. Entries of kind `acknowledge` (earlier builds') are read as `run`. The newest 200 within 30 days are kept, besides every one waiting, however old. Routines' plain notifications never come here (the notify plugin shows them itself); entries of the retired kind `routine` are dropped when the file is read
- **Waiting to be acknowledged**: one recorded with `acknowledge` true and waits while it has no `acknowledgedAt`; `notifications ack <id>...` or `ack --all` (an MCP tool too) sets that and prints those it acknowledged (`acknowledged`; one acknowledged already is no error, an unknown ID is, and acknowledges nothing). `notifications list --waiting` lists only those waiting. Every change to which wait (recording one, acknowledging) rewrites run status's `waiting` and `pendingAcknowledgements` at once, under its lock (each command after it and each scheduler pass do it again), so `status --watch` shows it within a second
- **Delivering one to acknowledge**: it's pending like any other (`list --pending`); the frontend shows one with `acknowledge` true and no `acknowledgedAt` with an Acknowledge action that runs `notifications ack <id>`, and with time-sensitive (macOS) or critical (Linux) urgency when `urgent`. A click on its body is `notifications open <id>` (`show-run`), as for any about a run, and doesn't acknowledge it
- **Delivered by frontends**, which mark them delivered (`notifications delivered <id>...`); `notifications list [--pending]` lists them. automator-ui delivers only while macOS allows notifications, so none are lost before the permission prompt is answered; the tray marks only those the desktop's notification service took
- **Clicking opens what it's about**: the frontend runs `notifications open <id>`, which says what to show and opens nothing: `open-url` (its `url`) for one with a link, which the frontend opens with the system's default handler (automator-ui `NSWorkspace.open`, the tray `xdg-open`), also for one waiting to be acknowledged (its Acknowledge button still acknowledges); `show-run` (its `routine` and `run`, and `hook` when it names a hook) for one about a run, `show-app` for one about the app itself (an update). The frontend shows it in its own windows
- **Opening** files and URLs uses `open` on macOS and `xdg-open` on Linux; `xdg-open` still running after 5 seconds has opened it (it may wait for the browser it started), one that fails before says so

## Usage limit
- **Checked when a scheduled run gets its turn**: over the limit, it's recorded as `skipped` with the reason (and a failure notification); manual runs and backfills go ahead, warning in their log. `usage [--json]` reports the backend in use (`kind`: `plan`, `budget`, or `none`); `doctor` reports it when over
- **`claude-code`**: `llm.usage-limit`, a share of the Claude plan's 5-hour and all-models weekly usage (single models' weekly limits are shown, not applied)
  - Read from Claude Code: `claude -p /usage` with stream-json output carries a `usage_report` (`rate_limits.limits`, rows by `kind`: `session`, `weekly_all`, `weekly_scoped`), read defensively, using no tokens
  - Kept in `plan-usage.json` with when it was read; read again when over 10 minutes old (when the scheduler starts, before a scheduled run, when `usage` is asked), never more often, even when it fails. A failed read keeps the last reading; with none, runs go ahead. A window past its reset is back at 0%
  - **Status line fallback**: `usage statusline install` sets Claude Code's `statusLine` (`~/.claude/settings.json`, nothing else changed) to run `procauto usage statusline`, which records the status line's `rate_limits` and runs the status line I had with the same input (saved in `statusline.json`); `usage statusline uninstall` and uninstalling the app put it back. Setup's `usage` step asks for it while `/usage` can't be read: it answered without a usage report the app can read, or 3 tries in a row failed (one failed try isn't enough; a reading clears it); an unreadable `/usage` isn't a health problem
  - A run that hits the plan's limit records it until the reset (an hour when it gives no time). No cost is recorded or worked out for these runs
- **`codex`** and **`local`**: none. The app can't read Codex's usage and records no cost for its runs or the local server's, so neither the plan's nor the API budgets apply (`kind: none`, never over); a run that hits Codex's own usage limit fails, saying so
- **`claude-api`**: budgets in USD per rolling window (`llm.budget.window`, `llm.budget.window-usd`) and per 7 days (`llm.budget.weekly-usd`), 0 meaning none: the sum of `claude-api` runs' `costUsd` (and older runs recorded as `api`), priced by the core from their tokens with a price table (cache reads, cache writes at 1.25× input, output); a model missing from it isn't counted, and its run's log says so. Runs on the local server are never priced (their cost is unknown, not zero), so they don't count

## The app's MCP server
- **`procauto mcp serve [--read-only]`** (stdio) serves the CLI as tools to Claude and other MCP clients. It's the app's interface, not a plugin: routines don't get it, and plugins that need the app's routines or runs reach it read-only through `Host.ConnectApp`
- **`procauto mcp connect`** registers it with Claude Code at user scope: `claude mcp add --scope user procauto -- <procauto> mcp serve`, by the `~/.local/bin` link when there is one (else `procauto` on `PATH`, else the running binary), so updates don't break it. It's connected when Claude Code's config (`.claude.json` in `$CLAUDE_CONFIG_DIR`, else in my home folder) has a user-scope `mcpServers.procauto` whose command exists; read from the file, no `claude` process. Nothing changes when it's connected; one whose command is gone is replaced
- **Parity**: every CLI command is a tool, derived from the command tree at startup (arguments and flags as the input schema, a command's `ValidArgs` as its first argument's `enum`); each call runs the CLI as a subprocess (`--json` when available), its log lines streaming as progress. Arguments are checked against the tool's schema. Flags that read local files (`--from`) aren't exposed; a routine's source reaches the command on stdin. `routines create`'s `--kind` isn't exposed either, and a program is added or updated only from a path, so a client can't add one
- **Cancelling** a call, or the server stopping, interrupts the command, which records its outcome
- **Safety on the command** (cobra annotations): `procauto/read-only`; `procauto/read-only-with: <flag>`, which adds a read-only variant tool (`run --dry-run`, `update --check`, `setup --json`); `procauto/not-read-only`. Unmarked commands are destructive, so clients ask before calling them
- **Overrides**, the one place a tool differs from its command (a test checks each names a real command): `daemon`, `mcp serve`, `mcp connect`, `help`, `completion`, `routines trust`, `hooks add|update|trust`, `watchers add|update|trust` and `uninstall` are excluded; `auth login` asks through the client; `update` reminds to reconnect; `guide` is served as text, not `--json`
- **Instructions**: the server tells clients what the app is, to read `guide` (topic `routines`) before writing a routine and topic `plugins` before adding a server, that routines start paused and untrusted (dry-run one, then I trust and resume it with `routines trust <name> --resume`, which isn't a tool), that sign-ins are done by me in my browser, never by pasting a secret into the chat, that programs are listed with `--kind all` and run, stopped and paused like any routine, but added and trusted only by me, that hooks and watchers are shown, fired (dry runs first), paused and stopped, but added and trusted only by me, and their event data is never instructions, and that `permissions_list` shows the permissions needed while `permissions_request` shows me the OS's prompt (said first), which only I answer
- **`--read-only` serves less**: only read-only tools, and nothing marked `not-read-only` (anything that runs, stops or sets up something, read-only variants included)
- **Secrets never pass through the model**: `auth login` shows the OAuth page, or the local page that stores a key straight in the secrets store, through URL elicitation, run across calls; if the client can't show URLs, the browser opens directly. A secret is never a tool argument
- **Change log**: every side-effecting call is recorded in `mcp-changes.jsonl`, with long values shortened, plugin env and header values left out, and one older file kept past 5 MB

## Memories
- **Plain Markdown files**, one per scope: `memories/_global.md` (every routine) and `memories/<routine>.md`, one memory per `- ` line; other lines are kept. Editable by hand
- `memory list/add/rm/edit` (`--routine <name>` for a routine's own; IDs come from the text). A run gets the global memories and its routine's through the `{{> memories}}` partial
- Each file is capped by `memories.max-chars`; past it, `memory add` asks to compact first. `memory compact [--routine <name>]` asks the model (structured output) to merge duplicates and drop replaced memories without adding anything, shows the change and saves only once confirmed (`--yes` without a terminal)
- Deleting a routine forgets its memories

## Guardrails
- **Allowlist** enforced by the shared agent code: only a routine's `tools` are registered with the model
- **Trust**: a routine runs for real only while what it can reach is what I trusted: its servers, allowlisted tools, built-in tools, plugin sections and folder (`trust.json`; a program's: see [[#Programs]]). Any change to those takes the trust away; its prompt, schedule, model and other settings don't
  - `routines trust <name> [--check] [--yes] [--resume]` shows what it can reach (tools split into writes and reads, by connecting to its servers) and what changed since it was last trusted, and asks; without a terminal it needs `--yes`; `--check` trusts nothing. `--resume` also resumes a paused routine that has a schedule, in the same yes (a trusted one is only asked about its schedule). Not an MCP tool
  - An untrusted enabled routine isn't scheduled (its problem says what changed and how to trust it); a real `run` of it is refused; dry runs never need trust
  - Created and installed routines start untrusted; deleting one forgets its trust. The first time trust is used, the routines already there are trusted as they are
- **Readiness**: an enabled routine whose folder is missing, whose built-in tools aren't the backend's, whose model's provider isn't set up, that uses a server nothing provides, lacks a required parameter, or needs a permission that isn't granted (or hasn't been checked) isn't scheduled either; its problem says why. `doctor`, `routines check`, `setup` and the scheduler judge a routine with the same checks
- **`doctor [--json]`** explains a red indicator without calling the model or any tool: the scheduler responds (run status fresh, no scheduler problem); each enabled routine loads, its settings resolve, its folder exists, its built-in tools are the backend's, it's trusted, its servers connect (signed in) and offer its tools, its model's provider is set up (the local server answers and has the model); every permission it needs is granted (a finding about one names it in `permission`, with `open`, the address of its settings page); its last run didn't fail, need a sign-in or get missed; usage is under its limit. Each finding has a fix; it fails if there are any

## automator-ui
automator-ui (SwiftUI, macOS 14+; `automator-ui/`, executable `AutomatorUI`, library `AutomatorUICore`) is the app: the indicator (menu bar icon with its status dot and menu, `Indicator/`), and the Settings, Setup, Routines and Hooks windows. It shows what the core says and runs what the core offers; the one thing it judges is whether the core is responding.
- **Every action is a CLI command** with `--json`, run off the main thread; each (but `status --watch`, `auth login`, which waits while I sign in, and `hooks fire`, which waits for its run) is stopped after 2 minutes, failing the call, as automator-tray's are
- **Follows run status** through `status --watch` (started again 5s after it ends); none yet, unreadable, or past `validUntil` (checked every 15s, so a stream that stopped goes red too) shows red, "Not responding". It reads no file and knows no path
- **Logo**: its icon and the indicator's glyph come from one source (`automator-ui/Resources/Logo/`): an hourglass drawn as one stroke whose head runs into the status dot
- **Menu**: one fixed width; text lines wrap or end in an ellipsis to fit (the full text on hover). The version; the status in the core's words (`reasons`, each opening its run with `runs show <id> --open`, one with `hook` the hook's window, on its run if it has one, one with only `routine` its window, one with `watcher` the watcher's window (`RunStatusReason.target`); else `summary`); Finish Setup… while `setupLeft` isn't empty; **Routines ›** (All Routines…, then each of `routines` with its `health` and `summary`, opening its window); **Hooks ›** while `hooks` isn't empty (All Hooks…, then each hook the same way); a routine or hook opened from the menu, without a run, opens on its Turn On review when its `turnOn` is true; the update item (Updating to X… while one installs, opening the Updating window); Settings; Quit
- **Settings window**: Start at login, the LLM usage card (`usage --json`), then the app-wide settings (`settings list --scope app`) as a collapsible tree from their dotted keys, one control per setting type (toggle, picker, text field, file chooser), shown and sent as text (`valueText`, `defaultText`); a text field saves on Return and when it loses focus; the core's message shows when it refuses a value; Reset; settings declared ahead of their feature are tagged and disabled. It re-reads everything each time it opens
- **A setting's choices**: under an enum setting's picker, the selected value's `enumHelp` line (e.g. what the chosen backend is)
- **Setup window**: `setup --json`'s steps grouped by kind, each with its button, and Check Again. The backend step's `settings` (the local backend's server and model) show under its choice, each with the Settings window's control. A turn-on step (a routine's; a hook's, with `hook`: one that's on but isn't trusted, or whose watcher isn't) shows the Turn On review (below) and its one confirm (`routines trust <name> --yes --resume`, which trusts a hook's watcher with it); each done, the next opens, one after another in the same window; an `auto` step runs once as soon as the window reads it, its button left for trying again
- **Turn On review** (`TurnOn` in `AutomatorUICore`, a sheet in a window): `routines trust <name> --check` (a hook's: `hooks trust <hook> --check`), read when it opens: the summary line, `warnings`, each of `permissions` that's `missing` or `not-checked` (its `label`, why from `by`, its state) with Grant…, each of `signIns` with Sign In… (`auth login <name> --browser`, then read again), the watcher it trusts with it, a missing watcher, `toolsError`, and Details (the surface or `program`, the watcher's `program`, `events` and `changes`) folded; one confirm, **Trust and Turn On** (**Turn On** when `trusted` and no watcher to trust): `routines trust <name> --yes --resume`, a hook's `hooks trust <hook> --yes --resume`. While a permission isn't allowed, the review is read again every 2 seconds and on run status changes, and says it won't run until it is; the confirm stays available. Grant… (`PermissionGranter`) runs `permissions request <permission> --json`, says what to do (answer the prompt when `asked`, and switch on the app `where` it says), and, when `state` isn't `granted` and the OS didn't ask (`asked` false), opens `settingsUrl`; once one it asked for reads `granted` (its answer, or what needs it read again), `granted` brings the window it was asked from to the front (`bringToFront`: macOS hands the focus to the app in front before its prompt); its failure shows by its row. A failed read shows why with Try Again, and the confirm stays disabled; a refused confirm shows why in the review, which stays open; once on, the window reads everything again. Opened by Turn On… (a window's header and banner while `turnOn` is true, a list's row), and by the menu and reasons as above
- **Permissions in a window**: a routine's, hook's and watcher's window shows its `show`'s `permissions`: a banner with the rows and Grant… while one is `missing` or `not-checked`, and a Permissions card in Overview with each one's state (`unknown` and `unsupported` left out); its detail is read again every 3 seconds while one isn't allowed, and when its run status entry's `problem` changes
- **Routines window**: each routine of either kind (`routines list --kind all`) with its health, schedule in words, last run and summary, leading to its window, and Turn On… beside one with `turnOn`. A program's window has no Memories tab and no model; its review shows the `program` section (executable, checksum, writes, arguments, secrets) in place of servers and tools
- **A routine's window**: Run Now / Dry Run (`start <routine> [--dry-run]`), Stop while it runs or waits (`stop`), Turn On… while `turnOn` is true, else Pause (`routines pause`; Resume under `…` for one with no schedule), Delete… (`routines delete`, confirmed); a banner while `turnOn` is true, saying why (`untrusted`, or paused), with Turn On…; its status, schedule with a days-and-time picker or custom cron (`schedule describe`/`build`, applied with `settings set` on Save), and what it can reach (read only); its runs (`runs show`); its memories; its own settings (`settings list --routine <name>`)
- **Hooks window**: each hook (`hooks list`) with its health and summary from run status's `hooks`, its kind, `on` in words ("When End key pressed (from nav-keys)": its `label`, else "a <type> event", else "any event") and its last run, with Turn On… beside one with `turnOn`; each watcher (`watchers list`) with its `mode` and `interval`, `trusted`, `enabled`, `hooks`, and `error` with `errorAt`; both read again when a hook's name, last outcome, being on or `problem` changes
- **A hook's window**: as a routine's, from `hooks show <hook>` and run status's `hooks`: **Fire…** (a sheet with the sample event as JSON, prefilled with `on.type`; `hooks fire <hook> --event-json <json> [--dry-run]`, with no time limit, showing its `RunOutput`) in place of Run Now; Stop (`stop`); Turn On… while `turnOn` is true, else Pause (`hooks pause`); Delete… (`hooks delete`, confirmed); a banner while `turnOn` is true (`untrusted`, else `problem`, else off), with Turn On…; when it runs (`on` in words, its `watcher` paused or failing), opening to its watcher (opening the watcher's window), `on.type`, `batch`, `staleness` and `rate`; what it can reach or runs (read only); Runs as a routine's, each opening to its `events` (type, `at`, watcher, `data` as indented JSON, plain monospace text); Memories for an LLM hook; Settings (`settings list --routine <hook>`) and its file (`source`, read-only)
- **A watcher's window**: `watchers show <watcher>`: its mode, interval and timeout, `lastPollAt` or `startedAt`, `lastEventAt`, `error` and `errorAt`; **Events it prints**: each of `events` with its label, type and the hooks acting on it, or `hint` as a sentence in grey; the hooks listening, each opening its window; what it runs (the review's `program`, without writes), Sign In… (`auth login <watcher> --browser`) for a secret not stored, and **Trust** (`watchers trust <watcher> --check`, then `--yes`; a failed read shows why, with Try Again); Pause / Resume (`watchers pause|resume`); Delete… (`watchers delete`, confirmed); its file, read-only
- **Updates**: `update --check` on launch and daily; "Update to X…" confirms with the core's `note`, then installs with `update --detach`, which runs in the background so it survives automator-ui restarting, logs to `update.log`, and reports its result as a notification. An install holds `locks/update.lock`, so a second one refuses and the menu shows one in progress
- **Update progress**: while one installs (started here, or reported by `update --check`), `update progress --json` every 2 seconds until its `state` isn't `installing`. The Updating window (opened on starting one, and from the menu's Updating item) shows its release, `step` and `detail` with an indeterminate progress bar, then the error if it failed; closing it leaves the update running
- **Start at login**: `login-items status|enable|disable` over the build's login items, `ui` and `scheduler`: on macOS launchd's enable/disable override on the installed LaunchAgents; on Linux the tray's XDG autostart entry, off when hidden (`Hidden=true`, or GNOME's `X-GNOME-Autostart-enabled=false`), and enabling the scheduler's systemd user unit. It never starts or stops what's running; `installed` is false before the app is installed
- **Starting and stopping now**: `login-items start|stop --json` (`scheduler`: running or stopped; `changed`; `uiStopped`), neither changing starting at login. `start` is idempotent: on macOS it loads the scheduler's LaunchAgent if it isn't loaded (turned on for the load and off again when it's off at login; tried again for a few seconds while launchd lets go of one just stopped; one loaded meanwhile is fine), on Linux `systemctl --user start` (without a user session, it says to run `daemon` another way). `stop` stops the scheduler (macOS: `launchctl bootout`, which KeepAlive doesn't undo, waiting up to a minute for its process to exit; Linux: `systemctl --user stop`), then the frontend running from the app's folder: on macOS the menu bar app's agent booted out and any other `AutomatorUI` there sent SIGTERM; on Linux the tray and the windows app sent SIGTERM. It spares itself and the process that ran it (a frontend's Quit), and a spared menu bar app's agent stays loaded: it exits successfully, which its agent doesn't restart. The MCP server offers `start`, not `stop`
- **Quit** (the menu's) hides the icon, runs `login-items stop`, then quits; when it fails, an alert says why first. The launch runs `login-items start`; opening the app while it runs (`applicationShouldHandleReopen`) runs it too and opens the Setup window while run status's `setupLeft` isn't empty, else Settings (`Lifecycle` in `AutomatorUICore`)
- **Notifications** (the app's own): `notifications list --pending --json` when run status changes and every minute; each is shown, then marked delivered (`notifications delivered`); a click runs `notifications open <id> --json`: `open-url` opens its `url` with `NSWorkspace.open`, else it opens the app there: `show-run`, the routine's window (the hook's, when `hook` is true) on its Runs tab with that run open and in view; `show-app`, the Routines window. One with `acknowledge` true and no `acknowledgedAt` is posted in the `acknowledge` category, whose **Acknowledge** action runs `notifications ack <id>` (a failure in an alert), time-sensitive when `urgent`
- **Acknowledgements window** (`Acknowledgements` in `AutomatorUICore`): `notifications list --waiting --json`, read again when run status's `waiting` ids change; each with its `title` and `body` (plain text), `routine`, `at`, Show Run (the routine's or hook's window on `run`) and Acknowledge (`notifications ack <id>`); Acknowledge All (`--all`); a failure shows above the list. The reason with `acknowledge` true ("(N) Acknowledgements pending") opens it
- Each window and its data are freed when it closes

## automator-tray (Linux)
automator-tray (Go; `automator-tray/`, its own module, so the core's dependencies stay its own and it can't import `core/internal`) is Linux's frontend: the tray icon with its status dot and menu, the app's notifications and updates, as automator-ui's indicator, Notifier and updates behave. It shows what the core says and runs what the core offers, through the CLI only, with the same one judgement (whether the core is responding). It builds for Linux only, CGO-free.
- **Its app**: it sits at `bin/automator-tray` beside the CLI (`bin/<Command>`) and reads the app from the package, as automator-ui reads its `Info.plist`: `share/<Folder>/install.env` (`NAME`, `COMMAND`, `VERSION`, `BUNDLE_ID`) and its icons in `share/<Folder>/tray/` (`--app <folder>` names that folder in development). It has no names of its own
- **The tray icon**: a StatusNotifierItem with a dbusmenu menu over D-Bus (`fyne.io/systray`, pure Go), whose Id is the app's name; a desktop needs a StatusNotifierItem host (GNOME: the AppIndicator extension). Its icons are PNGs made from the app's logo when it's packaged (`cmd/trayicons`: the glyph, light with a dark rim, with the dot in green, red or grey, bright and dimmed); while busy it shows the bright and dim ones in turn every 0.8 seconds
- **Follows run status** as automator-ui does: `status --watch`, started again 5s after it ends, the last status shown again every 15s so one past `validUntil` goes red
- **Menu**: as automator-ui's, rebuilt only when what it shows changes; a routine or hook row, and a reason about one with no run, opens its window with `review`; a reason with `watcher`, the watcher's window. Rows are plain text up to 80 characters (longer ones end in an ellipsis), with underscores shown as such; a routine's row carries its health as a coloured dot; rows that do nothing are disabled
- **Windows go through one function** (`tray.OpenWindow`): every window is the windows app's (`automator-windows <kind> [<name> [review]]`, below), started in a session of their own when it's beside the CLI and there's a display (`DISPLAY` or `WAYLAND_DISPLAY`); one that exits with an error within 3 seconds (no OpenGL, a display that won't open) is logged (what it said is in the tray's log), and its window opened in a terminal instead; so is the reason a window had none (no display, no windows app). Without the windows app or a display, a window runs its CLI command (Setup: `setup`; Settings: `settings list --scope app`; Routines: `routines list --kind all`; a routine: `routines show <routine>`, on its review `routines trust <routine> --resume`; Hooks: `hooks list`; Acknowledgements: `notifications list --waiting`; a hook: `hooks show <hook>`, on its review `hooks trust <hook> --resume`; a watcher: `watchers show <watcher>`; Updating: `update progress`; asking before an update: `update --ask`) in the first terminal found of `$TERMINAL`, `xdg-terminal-exec`, `x-terminal-emulator`, `ptyxis`, `kgx`, `gnome-terminal`, `konsole`, `xfce4-terminal`, `xterm` (each given the command as separate arguments, its own way: `-e`, `-x`, `--` or nothing), kept open until Enter; with none, a notification names the command to run
- **Notifications** (the app's own) through `org.freedesktop.Notifications` on a session bus connection of its own, as the app (its name, and `tray/app.png`, made from `AppIcon.icns`), with a default action: `notifications list --pending --json` when run status changes (not on a heartbeat: the same status, valid for longer) and every minute, each shown, then marked delivered (`notifications delivered`); a click runs `notifications open <id> --json`: `open-url` opens its `url` with `xdg-open`, `show-run` opens the run's report (`runs show <id> --open`), `show-app` the Routines window. One waiting to be acknowledged also has an `acknowledge` action (**Acknowledge**: `notifications ack <id>`), stays until dismissed, and is critical urgency when `urgent`; where the service shows no actions, the menu's reason and the Acknowledgements window are the way
- **Its own messages** (a run that doesn't open, the update check's answer) are notifications too. Installing an update asks in one, with **Update** and **Later** buttons and the core's `note`, then runs `update --detach`; a notification service without buttons has the windows app ask (`confirm-update`)
- **Nothing it waits for holds it up**: each CLI command it runs (but `status --watch`) is stopped after 2 minutes, each call to the notification service after 10 seconds, and the service's capabilities are asked again until it answers; following an update stops after 30 failed `update progress` in a row, then it checks again
- **One per app**: it owns `<bundle ID>.Tray` on the session bus, taking it from one already running, which quits
- **Quit and opening the app** as automator-ui's: Quit runs `login-items stop`, then ends the tray (a notification says why stopping failed); starting, it runs `login-items start`. `automator-tray --open` (the app menu's entry) calls `Open` on the running tray's object (`/<bundle ID as a path>/Tray`, interface `<bundle ID>.Tray`): it runs `login-items start` and opens Setup while `status --json`'s `setupLeft` isn't empty, else Settings; with no tray answering, it becomes the tray (taking the name) and does the same. Without `--open` it takes over as above
- **Its log**: `paths --json`'s `frontendLog` (`frontend.log` in the data folder), started again once it would pass 1 MB (the one before kept as `frontend.log.old`); stderr until it's open. It logs its start (name, version, pid), why the scheduler didn't start, and why a window opened in a terminal; the windows app's stderr is that file

## automator-windows (Linux)
automator-windows (Go and Fyne; `automator-tray/windows/`, a module of its own inside the tray's, using the tray's CLI runner, app discovery and window function) is the Linux counterpart of automator-ui's windows: the Setup, Settings, Routines, routine, Hooks, hook, watcher and Updating windows, as automator-ui has them (above), in Fyne's widgets. It shows what the core says and runs what the core offers, through the CLI only. It needs cgo (OpenGL, and X11 and Wayland through GLFW, both in one binary) and glibc 2.34 or later; X11's libraries are loaded when it runs on X11.
- **Its app**: it sits at `bin/automator-windows` beside the tray and the CLI and finds the app as the tray does (`--app <folder>` in development); a window's title is the app's name and the window's
- **One process per window**: `automator-windows setup|settings|routines|routine <name> [review]|hooks|hook <name> [review]|watcher <name>|acknowledgements|update|confirm-update` shows that window (`review`: on its Turn On review, when it needs one) and exits when it closes; nothing of it runs while no window is open
- **One window of each kind**, and one per routine, hook or watcher: the first process for a window holds `window-<kind>.lock` (a routine's: `window-routine-<the first 8 bytes of its name's SHA-256, in hex>.lock`, a hook's `window-hook-…`, a watcher's `window-watcher-…`; an exclusive `flock`) in `$XDG_RUNTIME_DIR/<bundle ID>/` (else `<temp>/<bundle ID>-<uid>/`) and listens on the `.sock` of the same name beside it; one started while it's held asks it, through the socket, to come to the front and read everything again (`raise`), or to do that and open its Turn On review (`review`), then exits with 0. A window that has closed lets go of both, and drops an ask that came in meanwhile
- **Drawn as it changes**: a window's content is made again on each change, and the window is drawn again at once
- **Its CLI calls** are the tray's: off the UI's thread, each stopped after 2 minutes but `auth login`, which waits while I sign in, and `hooks fire`, which waits for its run; what they answer is shown on the UI's thread
- **Setup window**: as automator-ui's, with a routine to fix opening that routine's window through `tray.OpenWindow`
- **Settings window**: as automator-ui's; a path's file chooser picks a folder, and the usage card is read again every 15 minutes while the window is open
- **Routines and a routine's window** follow run status through `status --watch` (started again 5s after it ends, shown again every 15s), as automator-ui's do. Routines: as automator-ui's, its Setup and Settings opening those windows, the list read again (`routines list --kind all`) when a routine's name, last outcome or being on changes. A routine's window: as automator-ui's, with the Turn On review above its tabs while it's open (automator-ui's, with Cancel and its one confirm), and tabs Overview (status; what it can reach, read only), Runs (its latest 50, the newest open; a run opens to its report, final text, every tool call with its arguments, and tokens, read with `runs show <id>`, and **Open Report**), Memories and Settings (the Settings window's rows for `settings list --routine <name>`, the schedule among them as its cron, and the routine's model and file); a program's has no Memories or model, shows what it runs in place of what it can reach, and its runs' exit code and output; Delete… is confirmed in a dialog, and the window closes once it's deleted
- **Permissions**: the review's rows, a window's banner and Permissions card are automator-ui's (`permissions request`, then, when the OS didn't ask, the settings page through Fyne's OpenURL, the app's name from the package; once one it asked for is allowed, the window's `RequestFocus`); the banner gives way to an open review; on Linux most are `unsupported`, so none show
- **Acknowledgements window**: automator-ui's, following run status; a notification's run opens its report (`runs show <id> --open`)
- **Hooks, a hook's and a watcher's window** follow run status too, and are automator-ui's, with the routine window's Runs and Memories; a hook's **Fire…** shows its sample event (a monospace text field) above the tabs, with **Close**, **Dry Run** and **Fire**, and how the run went
- **Updating window**: as automator-ui's (`update progress --json` every 2 seconds while `installing`). `confirm-update` first says what's available (`update --check --json`: the release and the core's `note`), with **Later** and **Update** (`update --detach`), then follows it in the same window

## Linux
- The Go core runs unchanged; per-OS pieces have Linux versions behind the same interfaces: secrets through `secret-tool`, opening with `xdg-open`, start at login through the scheduler's systemd user unit and the tray's XDG autostart entry
- The tray (automator-tray) and its windows app (automator-windows) instead of automator-ui
- Only templates for Linux (no `platforms`, or including `linux`) are offered
- **The display for programs**: a program (a hook's that opens an app, say) gets `DISPLAY`, `WAYLAND_DISPLAY` and the session bus from the scheduler's own environment, which under systemd is the user manager's: they're there when the desktop session imports them into it (GNOME and KDE do; otherwise `systemctl --user import-environment`)
