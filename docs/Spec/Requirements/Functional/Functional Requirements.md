## Platforms
- **macOS and Linux**: the same CLI, scheduler and routines on both
- **A menu bar app on macOS, a tray on Linux**: macOS's menu bar app (automator-ui) has the app's window too; Linux's tray has the same icon, menu and notifications and the same window

## Routines
- **Routines are files on my device**: the app ships with none; a routine is added or changed by adding or editing its file in the routines folder, with no app update
- **What a routine says**: what the model should do (the prompt), the servers it uses and the tools it may call, its schedule, and optional settings (below)
- **One routine, several accounts**: a routine can use two accounts of a plugin at once; a tool both offer is named with its server, and the model, run records and dry-run writes tell the two apart
- **Schedule per routine**: a cron schedule in local time, changeable without editing the file; a routine without one runs only by hand
- **Pause and resume**: any routine can be stopped from running on its schedule and started again without removing it
- **Run now**: any routine can be run on demand, in the terminal or in the background, as a dry run or for real
- **Backfill**: any routine can be run as of a past day (e.g. Monday's date, for a routine covering the previous workday, covers Friday)
- **Stop**: a run in progress or waiting its turn can be stopped; it's recorded as stopped, not failed
- **Missed runs**: if the computer is asleep or off at a scheduled time, the routine runs when the computer is next fully awake (not in a Mac's maintenance wake, which sleeps again within seconds), unless that's later than the routine's staleness window; then it's recorded as missed
- **Sleep mid-run**: a run cut off by the computer sleeping (its connections drop) runs again from the start, once, if it changed nothing yet
- **Create, update and delete**: from a file, validated first (its servers must exist and offer its tools, when they can be asked); deleting a routine removes its settings, trust and memories and keeps its run history
- **Optional per-routine settings**: each one left out keeps the default behaviour
  - **Timeout**: how long a run may take before it's stopped and fails
  - **Effort**: how hard the model thinks
  - **Folder**: the folder the run works in instead of an empty temporary one (e.g. a repository it checks), with its project instructions (`CLAUDE.md`, or `AGENTS.md` on Codex) as instructions
  - **Built-in tools**: which of the agent CLI's own tools the routine gets, in that CLI's terms (Claude Code's Read, Bash, Edit; Codex's shell, write, web search); none by default
  - **Save session**: keep the run's agent session and record its ID and backend with the run, so I can resume it with that CLI
  - **Concurrency**: wait its turn (default: one run at a time, manual runs included) or run alongside other runs. A routine never overlaps itself; a run waiting its turn shows as queued
  - **Parameters**: values that make a shared routine mine (a channel, a team), asked for at install and changeable later
  - **Platforms**: the operating systems it runs on

## Programs
- **A program is a routine that runs an executable instead of a model**: usually a binary compiled from Go, with a description file (`program.yaml`) giving what it runs, whether it writes, and optionally its description, arguments, schedule, staleness, timeout and secrets. "Routine" with no kind means an LLM routine; programs are named explicitly
- **Kept apart, run alike**: programs live in their own folder, apart from the routines folder, and share everything around a run with LLM routines: schedule and catch-up within staleness, missed runs, waiting for a full wake, keeping the computer awake, run now, backfill, pause, stop, timeout, trust, run status, history, notifications and the status dot
- **One name space**: names are unique across both kinds, and hooks and watchers (see [[#Hooks]]); adding a routine, a program or a template under a name one of them has is refused
- **Commands take either kind**: those given a name (run, start, stop, show, update, delete, pause, resume, trust, runs, settings) find it whatever its kind; where no name is given (listing, checking all, creating), no kind means an LLM routine, and `--kind program` or `--kind all` says otherwise. What only LLM routines have (memories, an LLM routine's settings) given a program's name fails with "X is a program"
- **Adding one**: from its description file, with the executable it names beside it; both are copied into the app's own folder, and that copy is what runs. It starts paused and untrusted. Updating one copies them again; deleting one removes its copy, settings, trust and secrets, and keeps its run history and data folder
- **Trust**: a program runs only while its executable and description file are the ones I trusted, dry runs included
- **Dry runs**: one that declares it writes is passed `--dry-run`; one that doesn't runs as it is
- **What it runs with**: the secrets it declares, as environment variables (signed in with `auth login <program>`), a fixed PATH, my home folder, the desktop session's display (so it can open an app), and its own data folder as its working folder; nothing else from the app's environment
- **Notifications**: a program (or a program hook) can have the app notify me, each a line in the file named by `$PA_NOTIFY`: a title, a message, a link a click opens, urgent, or to acknowledge; at most 20 a run, a bad line noted in the run's record without failing it, none on a dry run
- **Its outcome**: exit code 0 is success; a one-line summary it writes to the file named by `$PA_RESULT` is the run's reason; what it prints is kept with the run, up to a limit
- **Never in the run queue**: programs don't wait for LLM routines' runs, and aren't held back by the usage limit
- **Ending it**: stopping it, its timeout or the scheduler stopping ends it and everything it started
- **Sleep mid-run**: one that doesn't write runs again once after the computer slept during it; one that writes never does

## Hooks
- **A hook is a prompt or a program run on events, not on a schedule**: its action is a Dotprompt file (an LLM hook) or an executable with a description file (`hook.yaml`, a program hook), and its trigger says which watcher's events it acts on, of which of the types that watcher declares. A hook has no schedule, and a routine no trigger but its schedule
- **Watchers** are programs the app runs to learn that something happened: an executable with a description file (`watcher.yaml`), polled every interval (given where it left off, it prints what's new) or streaming (one long-lived process printing events as they happen, started again when it ends). Several hooks can listen to one watcher; prompts can't be watchers
- **Events**: each has an ID, a type, when it happened and its data. A watcher's event is acted on once, even when it's printed again or the app restarts
- **A watcher declares what it prints**: each event type with a label in words ("End key pressed"). A hook picks one of them: one listening for another type isn't added, and one left listening for a type its watcher no longer declares has a problem; leaving the type out still means every event. An event of a type the watcher doesn't declare is dropped and logged, and the watcher keeps working. A watcher that declares none prints any type as before, with a hint to declare them that's never a problem
- **In words everywhere**: what a hook acts on says the label and the watcher: "When End key pressed (from nav-keys)" ("a key.end event" when the watcher declares none, "any event" without a type), in the CLI, its review and the app's window; a watcher's screen lists its events with the hooks acting on each
- **Kept apart, run alike**: hooks and watchers live in their own folders, with their own commands (`hooks`, `watchers`), and never show among routines, not even with `--kind all`. A hook's runs share everything around a run with routines: trust, the run queue for an LLM hook (a program hook skips it), keeping the computer awake, waiting for a full wake, stop, pause, timeout, run status, history, notifications and the status dot
- **One name space**: names are unique across routines, programs, hooks and watchers; the commands that take a name find a hook by it (`stop`, `runs`, `routines pause`, `resume`, `trust`), and the routine-only ones (run, show, check) say it's a hook
- **Adding one**: from its file's path, in a terminal, an LLM hook validated as a routine is (its servers must exist and offer its tools, when they can be asked); a program hook's executable, and a watcher's, are copied with it, and the copy is what runs. A hook starts off and untrusted. Deleting one removes its copy, settings, trust and secrets, and keeps its run history
- **Trust**: a hook runs only while its action and its trigger are what I trusted, a program hook's dry runs included; a watcher runs only while its executable, and the events it declares, are what I trusted. Trusting a hook trusts its watcher too, while it isn't trusted: one review shows both, and one yes covers both. Trusting an LLM hook that can write warns that it acts on outside data
- **Trying one**: there's no run now for a hook; it fires with a sample event (a file or stdin), as a dry run or for real
- **What an action gets**: an LLM hook's prompt gets the event, or every event that waited for it when it takes them in batches, each text from the watcher marked as outside data; a program hook gets its event as JSON on stdin, and the desktop session's display, so it can open an app
- **Sleep**: an event older than the hook's staleness is dropped; a watcher isn't polled while a Mac is in a maintenance wake, and a poll due while it slept runs as it wakes
- **Floods and loops**: a hook starts at most its rate of runs an hour, and an event past it is dropped; one due to run more than three times its rate in an hour is paused, with a run saying why
- **Pause and resume**: a hook can be turned off and on; pausing a watcher stops it, and the hooks that are on and listen to it show that as their problem until it's resumed
- **Changes take effect at once**: trusting, turning on or off, pausing, resuming, adding, updating or deleting a routine, program, hook or watcher, a setting, and a permission allowed (asked for from the app, or turned on in the OS's settings after asking) reach the scheduler within about a second: a hook turned on hears its watcher's events from then, one paused stops its watcher, and the status shows it straight away

## Templates
- **Templates are shareable routines, programs, hooks and watchers**: files and folders in the repository's `templates/` folder, shipped with the app as files; the app ships none of its own and works with none. A routine's is its `.prompt` file; a program's, a hook's or a watcher's is a folder with its description file, its executable or the source to build it from, and `template.yaml`
- **Tags**: templates are grouped in tag folders, general to specific; those under `projects/<project>/` are for that project's members
- **Installing**: a routine template is copied into the routines folder, where it's mine to edit; its parameters are asked for and become per-routine settings. A program, hook or watcher template is added as I'd add one from its files, off and untrusted, its parameters asked for and filled into its description file; one shipped as source is built first, which needs its toolchain installed (the error names it). A hook's watcher is installed with it from its template when I don't have it, and they're offered as one: a hook template's entry carries its watcher's, and a watcher template a hook comes with isn't offered on its own
- **Per OS**: only templates for this OS are offered unless I ask for all
- **Versions**: a template can say its version, and optionally what changed in it; both are shown wherever templates, and what I installed from them, are listed. A version is there for me to see where I am at a glance; whether a template changed is told by its content
- **What I installed is remembered**: each routine, program, hook and watcher installed from a template keeps which template and version it came from, and the parameter values filled into it, so it can be told whether the template changed since, and whether I edited my copy
- **Template updates after an update**: when the app comes back from an update and a template I installed from changed, one window lists each one changed: a checkbox per routine, program, hook or watcher (all unchecked), with Select all; its installed and new versions and what changed; and, when I edited my copy, that overriding it replaces my edits. Override replaces the ones I ticked with the new template, filled in with my parameter values; Not now leaves them all as they are. A change I didn't take isn't offered again, only a later one
- **An override keeps what's mine**: the name, settings (on or off, schedule, parameter values) and memories stay; a new parameter takes its default, and one that needs a value I never gave isn't offered until I install it again. One I trusted stays trusted, since ticking it is trusting the new version; one I hadn't trusted stays untrusted. A hook's watcher is overridden with it when its template changed too, and one shipped as source is built again
- **Installed before installs were remembered**: a routine, program, hook or watcher with a template's name and kind is matched to that template once; when it's the template's content it's recorded as installed from it, otherwise it's offered as possibly edited
- **The same from the CLI**: listing what's out of date, overriding some or all, and not taking a change; Claude can list them and leave them as they are, but overriding is mine, since it keeps trust

## Plugins
- **A plugin is an MCP server**, written in any language: remote (OAuth, an API key in headers, or public) or a local command, or a folder of my own with a `plugin.yaml`
- **Adding one** needs no code; it's tried first and nothing is added if it doesn't work. Removing one forgets its credentials
- **Accounts**: a second account of any plugin that signs in (two Slack workspaces, two Google or Linear accounts) is a plugin of its own, under its own name, signed in with its own credentials; it's listed, signed in to, checked and removed like any plugin, saying which plugin it's an account of. Removing it forgets only its credentials
- **The `notify` plugin**: desktop notifications from routines; this app compiles it in
- **Apps a plugin needs running** (iMCP, say, which its server bridges to and waits for while it's quit): while routines or hooks use the plugin, setup has a step, done while the app runs, with **Open** (`plugins open-app <plugin>`); `plugins list` says whether it runs. Connecting to the plugin opens the app first, in the background, and a connect fails at once, saying why, when it isn't installed or doesn't start. While a routine or hook that's on (enabled and trusted) uses it, the scheduler keeps it open: it opens it when it isn't running, trying again after five minutes when it didn't start; `plugins.open-apps` off stops that
- **Sign-ins** are done once and refreshed unattended; one that can't be refreshed is reported as needing a sign-in, with the server named, and fixed from the CLI or the UI

## Permissions
- **What the OS must allow, known before the first run**: what runs code declares the permissions it needs: a plugin (a plugin folder, a server added by URL or command, a plugin compiled in), a program, a program hook and a watcher. The set is macOS's: input monitoring, accessibility, screen recording, notifications, full disk access, calendars, contacts, reminders, microphone, camera and automation; any other is refused. The notify plugin declares notifications
- **Prompts inherit theirs**: a routine or an LLM hook declares none; it needs those of the plugins it uses. A hook needs its action's and its watcher's
- **Trust covers them**: a review lists every permission it needs, what needs each and its state; one added later needs a new review
- **Checked by the scheduler, as the app**: every permission, on each of its passes; the CLI, the MCP server and the frontends show what it found, and "not checked yet" before it has, never granted and never a problem: only one that isn't allowed is
- **One that isn't granted is a problem from the start**: a routine, program or hook that needs it doesn't run and isn't healthy, its problem naming the permission and where it's turned on; a watcher isn't started while one it declares isn't. One that can't be checked (full disk access and automation, which macOS has no check for) or isn't checked on this OS is never taken for missing
- **A change starts health afresh**: when the scheduler finds that a permission something needs changed (allowed or taken away), or which ones it needs changed, its past bad outcomes stop counting: a routine's, program's or hook's last run (failed, missed, skipped) and a watcher's last error. It shows neither red nor green until it runs again (a watcher: until it works or fails again); its runs stay in history as they were, and one still not allowed stays a problem
- **Asking for one**: `permissions request <permission>` has the scheduler ask the OS, so macOS's prompt names the app (macOS asks once; after that, and for one an app can't ask for, it says where in System Settings it's turned on, with the address that opens it); `permissions list` shows what's needed, by what, and its state
- **On Linux** input monitoring is read access to `/dev/input`; the others aren't checked

## Model backend
- **Four backends**, chosen by a setting: Claude Code on my Claude plan (`claude-code`), Anthropic's API with my API key (`claude-api`), my own model server (`local`: Ollama on my machine by default, or another local or hosted OpenAI-compatible one, with an API key if it needs one), or OpenAI's Codex CLI on my Codex sign-in (`codex`). `local` and `codex` are experimental and untested, and said so where they're chosen
- **Routines name Claude models**: on `local`, every routine runs on the one model I set for the server, unless it names another model there (`local/<model>`). On `claude-api`, a routine that names `local/<model>` runs on my server too; routines that only do need no Anthropic key
- **Former names keep working**: a config, routine or template that says `api` (now `claude-api`), and the server's former setting, key and `openai-compat/<model>` models, work as before, with nothing to change
- **Usage limit, by backend**: on my Claude plan, scheduled runs don't start while the plan's 5-hour or weekly usage is above a share I set; with an API key, they don't start once API spend in a short rolling window or the last 7 days passes the budgets I set (runs on my own server have no price and don't count); on my own server and on Codex there's none (a run that hits Codex's own limit fails, saying so). A run that doesn't start is recorded as skipped with the reason (red indicator, failure notification); runs I start by hand still run, with a warning. `usage` shows where I stand
- **No cost for plan runs**: on Claude Code or Codex the app never works out a dollar cost

## Runs
- **Inspecting runs**: which ran, how each ended and why, with its inputs, every tool call with what it returned (clipped, secrets redacted), writes and final text, from the CLI and the UI (the tool calls folded until opened); also as a readable report
- **Run history and logs** are kept for a retention period I set
- **Exporting a routine's or hook's logs** (`routines logs <name>`, `hooks logs <name>`): one zip of its latest runs (5 unless I say how many, or since when), each as `runs show` prints it and as recorded, its file, and the scheduler's, `start.log`'s and the frontends' log lines from during those runs or naming it. What looks like a credential is redacted and my home folder is written `~`; the runs' text and tool results are kept as they were. It works for one that no longer loads, or was deleted, as long as it has runs
- **Reporting a bug** in a routine or hook (`routines report <name>`, `hooks report <name>`): opens a new issue on the app's bug-report repository in my browser, filled in with a title, what happened, where (the routine or hook and its kind, the app's version and OS, the backend) and its latest runs' outcomes, for me to read and submit from my own GitHub account. With logs included, they're exported as above and shown in the file manager, for me to drag onto the issue. `--dry-run` only prints the page's address. An app with no bug-report repository takes no reports and says to send the exported logs to whoever maintains it
- **Outcomes**: success, failed, needs a sign-in, missed, skipped (over the usage limit) and stopped
- **Structured results**: a routine can declare the shape of its result, so history and the UI show clean results instead of prose
- **Health check** (`doctor`): explains a red indicator, hooks' too, with a fix for each problem
- **Routine check**: whether a routine would run (its file, settings, servers connecting, every allowed tool existing, and its model's provider set up and, for my own server, answering with the model), without calling the model

## Notifications
- **From routines** (the notify plugin): a routine can send me a short desktop notification, a title and a message, shown by the app as one of its own notifications about that run (on macOS by the menu bar app, on Linux by the tray). An **urgent** one breaks through Focus/Do Not Disturb where the OS allows it and stays until dismissed; normal ones are quiet and fade. Clicking one opens its link (`url`, such as a pull request's) with the system's default browser, or, without one, the run that sent it, with its output. It has no settings, app-wide or per routine
- **To acknowledge** (the notify plugin's `acknowledge`): one a routine asks me to acknowledge (something I must act on, such as a request someone made of me) is the app's own notification, about its run, with an Acknowledge button; it waits until I acknowledge it, from the notification, from the app, or with `notifications ack` (one, or `--all`), and the indicator is red, saying how many wait, until none does. Clicking it opens its link if it has one, else the app on its run, as the app's own do, and doesn't acknowledge it. Waiting ones are kept however old
- **The app's own**: a desktop notification when a run (a routine's or a hook's) fails, needs a sign-in, is missed or skipped, saying which routine or hook, when and why (can be turned off), when an update installs or fails, and when setup has a step left that it hasn't told me about since the scheduler started (so at login while setup is unfinished, and when a step is added, such as a new routine to turn on), saying what's left, shown by the menu bar app on macOS and the tray on Linux. Clicking any notification opens only what it's about, never Setup or Settings as well; clicking one of these opens the app's window on the run it's about, in its routine's or hook's screen, on Updates (an update's) or on Setup (setup's). They don't depend on the notify plugin

## Status indicator
- **Icon** in the macOS menu bar, or the Linux tray, with a status dot:
  - **Green**: every enabled routine is fine. A routine with no runs yet is fine while its next run is ahead
  - **Red**: something needs me: a routine failed, was missed or skipped, needs a sign-in, can't be scheduled (a permission it needs not granted among the reasons), didn't start at its time or is stuck; a hook that's on failed, was missed, was paused past its rate, or can't run (its watcher missing, untrusted, paused or failing); setup isn't finished (it has steps left, among them turning on a routine, program or hook that isn't trusted, never or not since it changed, or whose watcher isn't, whether it's on or off (one added off was never turned on; one trusted and paused was paused on purpose, and is no step): those are one reason, setup's, and its line opens setup, where each is reviewed and turned on in a row, not a line each); a notification waits to be acknowledged; or the scheduler isn't responding. A watcher that's failing, untrusted, paused or missing a permission is one reason, naming the hooks that listen to it, however many there are
  - **Grey**: no routines or hooks are enabled
  - **Pulsing**: a routine is running (whatever the colour); in the Linux tray the dot dims and brightens
- Updates within seconds of anything changing

## UI
Managing the app is possible entirely from macOS's menu bar app (automator-ui), without a terminal. The CLI does all of it too; the UI is another way in, not a replacement.
- **One indicator**: the menu bar app runs once; a second copy (opened beside the running one, e.g. by macOS after a permission is granted) quits at once
- **Menu** (the menu bar app's and the Linux tray's): the version; the status in words (while notifications wait for me to acknowledge them, "(2) Acknowledgements pending" first, opening Acknowledgements; each reason the dot is red, opening the run it's about, or the routine's or hook's screen, on its review when it needs turning on, or the watcher's screen; while setup has steps left, one line, "Finish Setup (N to do)…", opening Setup); everything it opens shows in the app's window; then, between separators, **Manage Updates…**, which also says when a newer release is available or one is installing; **Routines ›** (all routines, then each with its status); **Hooks ›** while there are hooks (all hooks, then each with its status); Settings; Quit
- **Quit** stops the app: the menu bar app or tray, and the scheduler (no routine runs on its schedule until I open the app again); both start again at the next login. When the scheduler can't be stopped, it says why and quits anyway
- **Opening the app** starts the scheduler if it isn't running, so opening it after a Quit brings everything back; opening it while it runs opens Setup while setup has steps left, else Settings
- **The app's window**: one window for everything the app shows: a sidebar of sections, **Routines**, **Hooks** and **Acknowledgements**, then **Setup**, **Settings** and **Updates**, each saying what waits in it (how many notifications to acknowledge, how many setup steps are left, a newer release or one installing); ☰ hides and shows the sidebar. A routine, hook or watcher opened from a section shows in it, with **Back** to what it was opened from (⌘[ on macOS); what the menu, a reason or a notification opens shows in its own section (a routine under Routines, a hook or watcher under Hooks), the window brought to the front, never a second one. It opens centred, the same size each time, with the sidebar shown
- **Turning one on**: a routine, program or hook that's off or not trusted is turned on with two clicks: **Turn On…** (on its screen, beside it in Routines and Hooks, from the menu or a reason) opens one review, and one confirm trusts it (a hook's watcher with it) and turns it on. The review says in a line what it does, warns first, offers granting each permission the OS hasn't allowed yet (the app asks the OS; while it's still not allowed, its settings page opens, saying what to switch on for the app; the row turns allowed by itself once the scheduler has checked) and signing in to whatever it still needs, says plainly it won't run until they're allowed (turning on is still possible), and keeps what it can reach or runs folded underneath; when the core refuses, it says why there. While it's on, the one action is Pause
- **Acknowledgements**: each notification waiting for me to acknowledge it (what sent it, its title and text as written, when, and its run), with Acknowledge on each and Acknowledge All; it changes as soon as what waits does
- **Permissions on the screens**: a routine's, program's, hook's or watcher's screen shows the permissions it needs with their state, a banner with Grant… while one isn't allowed (a reason about it opens the screen there); ones that can't be checked or aren't on this OS are never shown as needed
- **Routines**: every routine, LLM routines and programs together, with its health, schedule in words, last run and status; Setup and Settings beside them
- **A routine's screen**:
  - status: last run (when, outcome, reason), next run, why it can't be scheduled
  - its schedule in plain words (e.g. "At 09:20, Monday through Friday"), edited with a days-and-time picker or a custom cron
  - what it can reach (trusting it is turning it on, above)
  - its runs: what each did, its tool calls and writes, and its output
  - controls: run now or dry run, stop, pause/resume, delete
  - **Export Logs…** (the zip, shown in the file manager) and **Report a Bug…**: a title, what happened, and **Attach logs** (off until I tick it, saying the logs hold the runs' text and tool results); it opens the issue in my browser, saying it's filed from my GitHub account and public on a public repository, and after it, which file to drag onto the issue
  - its memories (see, add, remove) and its own settings
  - for a program, the same screen with only these differences:
    - what it runs, in place of what it can reach: its executable (its SHA-256, copyable), whether it writes, its arguments, and its secrets, each with its variable and whether it's stored; signing in to the ones that aren't
    - what a dry run does with it, beside the controls
    - each run's exit code and output, saying when the output was cut down
    - its description file, read-only, with its description and data folder
    - deleting it says its run history and data folder are kept
    - no memories or model
- **Hooks**: every hook, LLM hooks and program hooks together, with its health, what it acts on in words, whether it's on, and its last run; and every watcher: how it runs, whether it's trusted or paused, the hooks listening, and why it's failing; how to add one
- **A hook's screen**: a routine's (a program's, for a program hook), with only these differences:
  - fire with a sample event (written as JSON), as a dry run or for real, in place of run now; pause and resume turn it off and on; no schedule or next run
  - what it acts on: its watcher (its state, opening its screen), the event type, batches, staleness and rate
  - its review covers its watcher; when it runs is a line (its watcher, the event type), with the rest folded
  - each run's events (type, time, data), shown as plain text
  - memories for an LLM hook only
- **A watcher's screen**: how it runs and last went, why it's failing, the events it prints with the hooks acting on each (or the hint to declare them), the hooks listening, what it runs with signing in to its secrets and trusting it alone (rarely needed), its file (read-only); pause, resume and delete
- **Setup**: every setup step with a button for each
- **Settings**: start at login, LLM usage, and every app-wide setting with a control for its type
- **Updates**: **Install updates automatically** at the top (on or off), saying why a newer release isn't installing by itself yet when it isn't; the installed version with its release notes, readable and scrollable; **Check for Updates**, which shows a newer release with its notes and **Install Now**, or says it's up to date (it shows it's working while it checks, and can't be pressed twice); an update installing, with what it's doing, and why one failed
- **Start at login**: on or off
- **Linux tray**: the same menu, updates, notifications and window; a routine's schedule is edited as its cron setting, with no days-and-time picker. With no display to show the window on, or without the windows app, each screen is its CLI command in my terminal (Setup: `setup`; Settings: `settings list --scope app`; Routines: `routines list --kind all`; a routine: `routines show <routine>`, on a run `runs show <run>`; Hooks: `hooks list`; Acknowledgements: `notifications list --waiting`; a hook: `hooks show <hook>`; a watcher: `watchers show <watcher>`; Updates: `update --ask`)

## CLI
- **Everything is a command**: every feature, including what the UI does, with `--help` on each
- **Settings**: one generic `settings list/get/set/reset` surface reads and writes any setting, app-wide or per routine; values are checked before they're saved and apply without a restart
- **Paths**: `paths` shows where the app keeps its config, routines, programs, hooks, watchers, run status, history, notifications, templates and the frontends' log
- **Guide**: `guide` explains, from the app itself, how to write a routine (`guide routines`) and how to add a plugin or write my own, with the permissions one can declare (`guide plugins`), how to write a program (`guide programs`) and how to write a hook and a watcher (`guide hooks`), with examples that work, as text or `--json`; `routines create`, `routines update`, `hooks add`, `watchers add` and `plugins add` point to it
